# 質の問い

変更の質を確かめる問いである。エージェントは計画と実装の前に、レビュー役はレビューの前にこのファイルを読む。理由は、ハーネスの[計画、実装、レビューで同じ質の問いを使う判断の記録](../docs/decisions/0022-quality-question.md)に書く。

## 工程ごとの使い方

作る側（計画と実装をするエージェント）とレビュー役は、同じ問いを使う。基準をそろえ、使い方だけを工程で変える。

| 工程 | 使い方 |
|---|---|
| 計画 | 問いの答えを決めて、変更の記録に書く。 |
| 実装 | 決めたことを守る。 |
| レビュー | 決めたことと差分を比べる。 |

当てはまらない問いは飛ばす。問いや設計の原則を当てはめること自体を目的にしない。導入先の既存の書き方を先にする（[`rules/always-read.md`の節「導入先で書き方を決める順」](always-read.md#導入先で書き方を決める順)）。

## 案の比べ方

問いは、変更を確かめるほかに、案を比べる観点にも使う。観点どうしは両立しないことがあり（例：簡単さと将来、既存への影響と業界標準）、すべてを同時には満たせない。理由は、ハーネスの[質の問いを案を比べる観点にも使う判断の記録](../docs/decisions/0033-option-comparison-viewpoint.md)に書く。

案を決めるとき（例：変更の記録の判断、残す候補の勧め、実装の中の選び方）は、次のようにする。

- 案ごとに、差が出る観点で、得るものと失うものを書く。差が出ない観点は書かない。
- 規則か確認を足す案では、機械で止める所（スクリプトのように、同じ入力に毎回同じ結果を返す所）と、書く人とレビュー役の判断に残る所を分けて書く。どこまでが毎回同じに止まり、どこからが読む人で変わるかが見えないと、人が案の確かさを比べられないためである。
- 失うものには、あとで戻せるかを書く（例：消したデータ、公開した履歴、配った設定は戻しにくい）。戻せない失うものは、次の項目の影響度で、害が大きい側に入るためである。
- 失うものの重さは、起きたときの害（影響度）と、起きる条件が今の環境にあるか（緊急度）で比べる。2つの問いの答え方は、[`rules/review.md`の節「優先度の決め方」](review.md#優先度の決め方)のとおりにする。
- 作る手間と直しの量（例：直すファイルの数）は、直しが多くて成果物の精度が落ちる場合（例：直しの漏れ）を除き、成果物の精度より先にしない。導入先の作業の成果物を、要求に沿った質で作れることが目的のためである。
- 残すかを決めるときは、今の作業の中で解消する案（PRを作る作業では、このPRの中で解消する案）も並べる。優先度が中か低の候補では、行わない案も並べる。
- 行うかは、優先度（[`rules/review.md`の節「優先度の決め方」](review.md#優先度の決め方)）と、行う手間（例：直しの量、レビューの回数）を比べて決める。前の項目の、作る手間を精度より先にしない比べ方は、行うと決めたものの作り方を選ぶときに当てる。今の環境で起きない候補まで手間を数えずに行うと、確かめと直しが続いて作業を区切れないためである。
- 勧める案と、優先した観点と、その理由を書く。

## 問い

| 観点 | 問い | 指摘のラベル |
|---|---|---|
| 目的 | 誰の何が解決すれば満たしたと言えるか？受け入れ条件を確かめられる形で書いたか？ | `MUST` |
| 業務 | 業務のルール、用語、変えてはいけない動きを推測で補っていないか？ | `MUST` |
| 既存への影響 | 既存の機能、データ、利用者、運用の手順のうち、変わるものと変えないものを書き、影響を受ける所（例：呼び出し元、保存したデータ、手順書）を確かめたか？ | `MUST` |
| 異常系 | 失敗、重複、競合、境界の値でどう振る舞うかを決めたか？ | `MUST` |
| 非機能 | 性能、可用性、セキュリティ、運用のうち、この変更に関わるものと目標の値を書き、満たしたか？性能は、変更の前後の測定値で見る。 | `MUST`か`SUGGESTION`（表の下の箇条書き） |
| 堅牢性とセキュリティ | 不正な入力、権限、秘密情報の漏れ、依存の追加、外部の障害、タイムアウト、再実行で壊れないか？誤った結果、データの破損、戻せない変更が起きないか？ | `MUST` |
| 検証 | 要求と異常系をテストで確かめ、テストを弱めていないか？導入先に変異のテスト（コードをわざと壊して、テストが落ちるかを見る仕組み）があれば、それで確かめたか？ | `MUST` |
| 責務 | 変わる理由の違うものが、1つの単位（例：関数、ファイル、モジュール）に混ざっていないか？ | `SUGGESTION` |
| 依存 | 依存の向きが既存の構成に合い、変更の影響が狭い範囲に収まるか？ | `SUGGESTION` |
| 簡単さ | 今の要求に要らない抽象や機能を足していないか？ | `SUGGESTION` |
| 一貫性 | 既存の形、名前、同じ処理を確かめたか？既存に無いものは、公式の推奨と業界標準を確かめたか？ | `SUGGESTION` |
| 運用と文書 | 障害を調べられ、戻せるか？使い方が変わるなら文書も直し、コメントには理由を書いたか？ | `SUGGESTION` |
| コスト | 作る、保つ、覚える手間と費用（例：実装とレビューの量、依存の更新、チームが覚えること、使用量の料金）を、案ごとに比べたか？ | `SUGGESTION` |
| 将来 | 前提（例：使う量、決まっている計画、使っているバージョンのサポートの期限）が変わったときに、作り直さずに済むか？ | `SUGGESTION` |
| 最近の動向 | 使う技術の、直近（目安で6か月、根拠の資料は無い）の公式の発表（例：リリースノート、非推奨、脆弱性の勧告）を確かめたか？攻撃や障害の事例の報告（例：サプライチェーンの攻撃の報告）も確かめたか？ | `SUGGESTION`か`MUST`（表の下の箇条書き） |

`MUST`の範囲は[`rules/review.md`の節「ラベルの付け方」](review.md#ラベルの付け方)で決めていて、問いの表のラベルはその当てはめである。迷いやすいものは、次のように分ける。

- 変更の記録で決めたことから外れるものは、依頼の問題なので`MUST`にする。
- 非機能では、変更の記録かチケットに書いた目標の値を満たさないものと、セキュリティの問題を`MUST`にし、ほかは`SUGGESTION`にする。
- 最近の動向でも、脆弱性の勧告か攻撃の事例に当たるものは、セキュリティの問題なので`MUST`にする。
- 既存への影響は、正しさと範囲の問題なので`MUST`にする。

最近の動向で攻撃や障害の事例の報告も確かめるのは、使う技術の公式の発表には、その技術の不具合でない攻撃や障害（例：npmのパッケージのワームが、Claude Codeの設定にフックを書いた攻撃）が載らないためである。

レビュー役は、表の問いのほかに、作業の範囲の外を変えていないかと、機械の確認の出力があるかを見る。この2つは、作る側には問わない。

## 指摘の書き方

指摘には、どの入力か変更で何が困るかを書く。書けない指摘と、仕様や入力の形の上で起こりえない場合のための指摘は出さない。問題を探すよう頼まれたレビュー役は何かを見つけ、すべてを直すと余分な抽象化とテストが増えるためである（Best practices for Claude Code）。
