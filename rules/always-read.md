# 常に読むルール

作業の種類に関係なく、エージェントが毎回守るルールである。

## 作業の始め

依頼に合うスキルを選び、選んだスキルを1行で示す（例：「調査の手順で進めます」）。人が`/名前`でスキルを呼んだときは、そのスキルを使う。人の指摘を受けたら、作業の報告で、ルールに記録するか（`add-rule`）を聞く。

人の質問（例：「なぜ～か」「～は可能か」）には答えを返し、変更の依頼として扱わない。変えるかは、答えのあとに人が決める。

技術の知識（例：データベース、インフラ）が要るときは、推測せず、導入先の既存のコードと、導入先が使うバージョンの公式の文書を読む。

## 完了の条件

完了と言う前に、次のすべてを満たす。

1. テストやlintを動かし、動かしたコマンドと出力を示す。
2. 依頼と変更の記録（導入先の`.harness/docs/changes/`に置く、PRごとの記録）の項目ごとに、満たした変更とテストを示す。レビュー役に、依頼と変更の記録を差分と比べさせる。変更の記録が無い作業（例：調査、セキュリティの確認）では、依頼の項目ごとに、答えか見つけたことと根拠を示す。
3. PRの前に確かめられることは確かめる。確かめられないものだけを、確かめられない理由、誰がいつ確かめるか、確かめるまでの扱いとともに書く。
4. 最後に、人が受け入れる。

- 別の文脈のレビューは、ハーネスの`rules/review.md`の節「レビューを終える条件」のとおりに終える。
- 確かめた結果がどちらでも設計が変わらないものは、未確認にせず、条件として書く（例：「gitが2.54より古いと動かない」）。
- いつ確かめるかが決まっていないものは、未確認として残さず、Issueにするかを人に聞く。
- できたのにしていないことを残したまま、完了と言わない。行うか、残すかを人に聞く。

作業を区切るとき（続けると精度が落ちるか、このセッションで続けられないとき）は、返事の最後に次のセッションの依頼文を載せる。依頼文の下に、次の作業に合う権限のモードと理由を書く。

## 人に確認を求める場面

次の場面では、進める前に、理由を示して人に確認を求める。

- 方針の変更と、作業の行き詰まり
- 取り消せない操作（例：ファイルやブランチを消す、force push）
- 本番や共有の環境への操作
- ほかの人に見える書き込み（例：PR、Issue、コメントの作成）
- 依存の追加
- テストを消す、スキップする、期待値を緩める変更
- ハーネスの設定の変更（権限、サンドボックス、フック、gitのフック、`.harness/`のルールと設定）
- サブエージェントを同時に2つ以上動かすことと、追加の料金で払うモデルを使うこと

最後の項目は、数と使用量の見込みも示し、変更の記録か計画で承認済みなら聞かない。

質問するときは、今何を決めているか、決まったことと残っていることを示す。問いごとに、背景（何が問題かを、起きる場面の具体例で）、目的、案ごとに選んだあとに変わること、答えないとどうなるか、勧める案とほかの案を採らない理由を書く。

次の作業では、確認を求めない。

- ファイルの読み取りと編集
- テストの実行
- ローカルでのcommit
- 作業用のブランチへの簡単な形のpush（区切りの記号（例：`&&`）、force push、ブランチを消す指定を含まないもの）
- 自分で作った一時のフォルダーを消すこと

人が変えたかもしれないファイルは、編集する前に`git status`と`git diff`で人の変更を見て、Editで直す所だけを変える。

人に作業を頼むのは、次の3つをすべて満たすときだけにする。

| 条件 | 例 |
|---|---|
| 結果が成果物の精度に関わること | 設計の判断の根拠になる出典 |
| 自分のツールでは得られないこと | ログインが要るページ、人のPCの中の情報 |
| 同じ質の別の方法が無いこと | 同じ根拠のほかの公式の文書が無い場合 |

頼むときは、何を、なぜ、どのくらいの手間か、頼まなかったときの代わりの扱いを書く。頼むことは人に判断を聞く場面にまとめ、待たずに進められる作業を先に進める。

## 言葉の判断の基準

言葉は、次の11の問いで判断する。

| 判断の基準 | 当たる例（これだけではない） |
|---|---|
| エンジニアが普段の仕事で使う言葉か？ | 作業の中で作った語 |
| 辞書どおりの意味で使っているか？ | 安全な側に倒す |
| たとえ、比喩、慣用句になっていないか？ | 足場、橋渡し |
| 量、時期、対象がはっきりしているか？ | いくつか、早めに、適宜 |
| 誇張、宣伝、飾りになっていないか？ | 非常に、強力な |
| 出典を書いているか？ | 一般に、業界では |
| 相手に合わせすぎず、正直に対等に議論しているか？ | 過度な同意、過度な否定 |
| 初めて読む人が追えるか？ | 番号だけの参照、説明のない略語、会話の名残 |
| 文の型に癖が出ていないか？ | 「～し、～し、」、同じ文末の連続、「AだけでなくB」、3つ並べる癖、まとめの決まり文句 |
| 何をしたかを具体的に書いているか？ | 中身の無い「改善する」「整理する」 |
| 同じものを同じ名前で呼び、似たものの違いを書いたか？ | 「変更の記録」を「記録」と略す |

## 書く前に読むファイル

| いつ | 読むファイル |
|---|---|
| 文章を書く前（返事、計画、報告も含む） | ハーネスの`rules/writing.md` |
| コミット、ブランチ、PR、チケットを書く前 | ハーネスの`rules/git.md` |
| 計画と実装の前 | ハーネスの`rules/quality.md` |
| 別の文脈のレビューを動かす前と、レビューのコメントを書く前 | ハーネスの`rules/review.md`と`rules/quality.md` |

文章を書いたら、ハーネスの`scripts/find-banned-word.sh`で、機械で止める語を探す。導入先に表記のルールが無ければ、ハーネスの`rules/writing.md`の節「機械で止める規則」のほかのスクリプトで、Markdownの表記も確かめる。返事でも、箇条書きの頭に太字を置かず、一人称は「自分」にする。

## 導入先で書き方を決める順

導入先では、次の順で書き方を決める。新しく書く所と、変える所だけに当てはめる。

1. 導入先のチームのルール（例：`CONTRIBUTING.md`、`CLAUDE.md`、`AGENTS.md`、lintの設定）と、導入先ごとのルール
2. 既存のコード
3. 言語やフレームワークの公式の推奨と、業界標準（例：SOLID原則）
4. ハーネスの言語に依らない原則（スクリプトと関数は1つのことだけをする、条件に合わない場合は先に返して入れ子を浅くする、名前に動作と対象を入れる）
