# レビューのルール

レビューのコメント、指摘の流れ、レビューの深さと使用量の見込み、終わり方のルールである。エージェントとレビュー役は、別の文脈のレビューを動かす前と、レビューのコメントを書く前にこのファイルを読む。何を見るかは[`rules/quality.md`](quality.md)に書く。規則の理由は、節ごとに、ハーネスの判断の記録へのリンクで示す。

## レビューのコメント

人に向けた書き方と言い方は、[`rules/writing.md`の節「人に向けた書き方」](writing.md#人に向けた書き方)に従う。

コメントの意図は、頭のラベルで示す。`MUST`は、必ず満たすことを表す。

| ラベル | 意味 |
|---|---|
| `MUST` | マージの前に直す。 |
| `SUGGESTION` | 直すとよい。マージは止めない。 |
| `QUESTION` | 聞きたいことがある。 |
| `FYI` | 共有する。マージは止めない。 |
| `NICE` | 良いと思った。マージは止めないが、大事さは低くない。 |

- GitHubとGitLabでは、ラベルをshields.ioのバッジにして、1つ目の段落にバッジだけを置き、指摘の文は空の行のあとの2つ目の段落から書く。画像を出さない表示（例：通知のメール、外の画像を出さない自前のGitLab）でも、画像の代わりの文字（例：`MUST`）が次の文とつながらないためである。GitLabのコメントでバッジが画像で出ることは、gitlab.comで確かめた。
- ほかの場所（例：Jira、チャット）では、1つ目の段落にラベルの語だけを置き、指摘の文は空の行のあとの2つ目の段落から書く。人が、ラベルと文の境目をすぐに見分けられるようにするためである。改行1つでは、gitlab.comのコメントでラベルと文が1行につながって出たので、どの場所でも分かれる空の行で分ける。
- レビュー役のサブエージェントの報告も同じラベルを使い、根拠の`path:line`を付けて短く書く。

バッジは、ラベルごとに次の色で書く（`MUST`は、GitHubの既定のラベルの赤）。色をラベルごとに1つに決めるのは、読む人がラベルを色でも見分けられるようにするためである。

```markdown
![MUST](https://img.shields.io/badge/MUST-d73a4a)
![SUGGESTION](https://img.shields.io/badge/SUGGESTION-0075ca)
![QUESTION](https://img.shields.io/badge/QUESTION-5319e7)
![FYI](https://img.shields.io/badge/FYI-cfd3d7)
![NICE](https://img.shields.io/badge/NICE-0e8a16)
```

エージェントがGitHubかGitLabに送るコメントのうち、答えたことを示すものと、人の判断を待つものには、最後の行に、表示されないHTMLのコメント`<!-- my-harness -->`を付ける。例は、スレッドへの返信、PRに残す候補（直さずに残すかを人が決める指摘）のコメント、PRへの普通のコメントである。

- 付けるのは、`resolve-review-comment`が、答えたかを、書いた人の名前でなく`<!-- my-harness -->`で見分けるためである。`resolve-review-comment`は、自分のPRに付いた指摘に答えるスキルである。
- ほかの人のPRに送るレビューのコメント（`review-pr`のスキルが作る）には付けない。PRの作者の答えを待つ指摘に`<!-- my-harness -->`があると、作者の`resolve-review-comment`は、その指摘を答えたものとみなして、答える指摘から外すためである。
- `<!-- my-harness -->`で見分ける形と比べた案は、ハーネスのリポジトリの[`.harness/docs/features/skill.md`](../.harness/docs/features/skill.md)に書く。

### 人に判断を求める指摘の形

次の場所で、人に直すかを決めてもらう指摘は、下の表の6つの小さな見出しで分けて書く。読む人が、何の指摘か、どれだけ急ぐか、受け入れるかどうかで何が変わるかを、ほかの文書を開かずに判断できるようにするためである。

- PRを作る前の確認（エージェントがPRを作る前に、本文の下書きと残す候補を人に示す場面）で示す指摘の一覧と、PRの該当箇所へのコメント
- PRの無い作業（例：セキュリティを確かめる`audit-security`）の完了の報告
- ほかの人のPRへのコメントの案

見出しの「受け入れる」は、指摘の勧めのとおりに直すことである。

| 見出し | 書くこと |
|---|---|
| 何の指摘か | 指摘の中身を1～2文で書く。 |
| 起きること | 最初の1文で、どう確かめたか（動かして確かめた、コードを読んで判断した、まだ動かせないので想定した場面）を書く。そのうえで、どの入力か変更で何が起きるかを書く（[`rules/quality.md`の節「指摘の書き方」](quality.md#指摘の書き方)）。 |
| 急ぐか | 節「優先度の決め方」の2つの問い（起きたときの害と、今の環境で起きるか）と、決まっている作業（例：リリースの予定、次のPR）を止めるかに答える。そのうえで、すぐ決めるべきか、いつまでに決めればよいか、直さなくてよいかを書く。 |
| 受け入れると | 何が変わり、何を失うか（例：減る字数、増える手間、消える理由の文）を書き、受け入れたあとの例（例：直したあとの文、出力）を添える。動かしていない例は、コードや文から引いたものか、想定かを書く。 |
| 受け入れないと | 何が残り、誰がいつ気づくかを書き、そのままのときの例を添える。動かしていない例は、コードや文から引いたものか、想定かを書く。 |
| どうするとよいか | 「○○なら、こうする」「○○なら、しない」の形で、条件ごとの勧めを書く。最後に、自分の勧めを、人が選ぶ扱いと同じ語（例：このPRで直す、あとで行う、行わない）で、理由とともに書く。 |

見出しの中身は、次のことも守る。

- 「起きること」では、手元で動かせるものは、手間が見合えば動かし、出力も書く。「コードを読んで判断した」は、動かせないときか、動かす手間が見合わないときに限る。
- 「どうするとよいか」では、案が複数あれば、案ごとに条件を書く。案には、今の作業の中で直す案（PRでは、そのPRの中で直す案）も入れ、[`rules/quality.md`の節「案の比べ方」](quality.md#案の比べ方)のとおりに比べる。
- ほかの人のPRの`MUST`は、直すことが決まっている。そのため、「受け入れると」と「受け入れないと」を省き、「どうするとよいか」では直し方の案だけを比べる。「急ぐか」には、節「優先度の決め方」の問いに答えず、マージの前に直すことと、その理由だけを書く。
- 最後の勧めを人が選ぶ扱いと同じ語で書くのは、別の語（例：「残すのがよい」）では、人が勧めのとおりと答えたときに、扱い（例：あとで行うか、行わないか）が2つに読めるためである。

書き方と並べ方は、次のとおりにする。

- 見出しごとに段落を分け、続けて書かない。[`rules/writing.md`の節「人に向けた書き方」](writing.md#人に向けた書き方)の「結論、理由、依頼」で段落を分ける書き方より、この形を優先する。
- 複数の指摘を示すときは、急ぐものから並べる。GitHubの該当箇所へのコメントのように並べ替えられないときは、コメントをまとめたレビューの本文に、決めてほしい順とその理由を書く。
- この形で示す指摘には、優先度の高、中、低を付けない。優先度は、人が残すと決めたあとに付ける（例：PRの本文の「残っていること」に書くとき、チケットにするとき）。
- ファイル、行、節、チケットへの参照は、リンクにする。GitHubとGitLabでは、マージでブランチが消えても切れないよう、pushしたあとのコミットのSHAで固定したURLにする。pushの前のSHAは、向き先のブランチの取り込み（`git rebase`）で変わることがあるためである。GitHubでは、Markdownのファイルの行を`?plain=1#L10`で指す。GitLabのURLの形は、`review-pr`と`resolve-review-comment`の`references/gitlab.md`に書く。

PRの本文の「残っていること」は、人に判断を求めず、決まったことを短く残す表なので、この形にせず、[`rules/git.md`の節「PRの題と本文」](git.md#prの題と本文)の表の形にする。レビュー役のサブエージェントの報告も、この形でなくてよい。変更を書いた本人が報告を読んで確かめ、人に示すときにこの形に書き直す。

## 指摘の流れ

指摘を受けたら、「このPRで直すか」と「残したものをどの順に行うか」を分けて決める。依頼の抜けと表示の崩れを1つの尺度に入れると、どこに基準を置いても、どちらかの扱いを誤るためである。

| 問い | 何で決めるか | 結果 |
|---|---|---|
| このPRで直すか | ラベル | `MUST`は直してからマージする。`SUGGESTION`は直さなくてもマージできる。 |
| 残したものをどの順に行うか | 優先度 | 残すものにだけ、ラベルとは別に優先度を付け、高いものから行う。 |

### ラベルの付け方

| ラベル | 対象 |
|---|---|
| `MUST` | 正しさ、依頼と変更の記録（ほかの人のPRでは、PRの本文とチケット）、テスト、作業の範囲、セキュリティに関わる問題 |
| `SUGGESTION` | 変更の質の問題（責務、依存、簡単さ、一貫性、運用と文書、コスト、将来、最近の動向） |
| `FYI` | 「前から」の誤り（PRの差分より前からある、PRが入れていない誤り） |

- `MUST`は、この範囲に絞る。[`rules/quality.md`の節「問い」](quality.md#問い)のラベルは、この範囲の当てはめで、問いを足しても範囲は広げない。理由は、ハーネスの[`MUST`の範囲の判断の記録](../docs/decisions/0007-must-finding-scope.md)に書く。
- 文章の書き方は、[`rules/writing.md`](writing.md)の表の「誰が確かめるか」のとおりに見る。読み手が事実を誤って読む所は、正しさの問題として`MUST`にする。動かすと決まっている確認（例：テスト、lint、文章の確認。[`rules/always-read.md`の節「完了の条件」](always-read.md#完了の条件)と[節「書く前に読むファイル」](always-read.md#書く前に読むファイル)）の出力が無いときも、`MUST`にする。変更が当たらないので動かさなかったテストを、名前と理由とともに示していれば、出力が無いことに数えず、理由が差分に合うかを見る。合わなければ、出力が無いものとして`MUST`にする。
- 「前から」は、PRが入れていない誤り（PRの差分より前からあり、PRの変更とは関係なく誤っている所）だけにする。PRの変更で、変えていない所が誤るようになったもの（例：名前を変えて、古い名前の参照が残る）は、PRが入れた誤りなので`MUST`にする。
- 「前から」の誤りをそのPRで直すかは、書いた本人が決めず、節「残した指摘の置き場所」の表の場面で人が決める。節「レビューを終える条件」の表の「直し方」の行のとおりに、同じ種類の誤りを探して見つけたものも、書いた本人が決めず、人が決める。直すと、人が変更の記録で承認した範囲より、PRが広がるためである。
- 導入先のチームのルールか導入先ごとのルールに重要な部分（例：決済、認証）が書かれていれば、そこでは、正しさやセキュリティに関わるか迷う指摘も`MUST`にする。
- `SUGGESTION`と`FYI`の指摘は、レビューを終える条件（`MUST`の指摘が無いこと）に数えない。
- チケットに分ける案にした`MUST`（節「3回目で残った指摘の直し方」）と、書いた本人が退けて人に示す`MUST`（節「レビューを終える条件」）も、レビューを終える条件に数えない。

### 優先度の決め方

優先度は、起きたときの害（影響度）と、起きる条件が今の環境にあるか（緊急度）で、次のように決める。影響度と緊急度で決めるのは、ITサービスの運用の手引きであるITILの、インシデントの優先度と同じ形である（Checklist Incident Priorityの「Definition」）。それぞれを2段階にするのは、組み合わせを4つにして、1件ずつ決める手間を減らすためである。

| 起きたときの害 | 今の環境で起きる | 今の環境では起きない |
|---|---|---|
| 気づかないうちに誤るか、戻せない（例：誤った結果の通過、データの破損、秘密情報の漏れ） | 高 | 中 |
| 気づけて、直せば害が止まる（例：エラーでの停止、表示の崩れ、手間や費用の増加） | 中 | 低 |

表には、次のように当てはめる。

- 今の環境は、今動かしているか、動かすと決めている環境と機能である（例：本番、CI、開発の環境、サポートすると決めたブラウザー、作ることかリリースすることが決まった機能）。動かすと決めていない環境は、利用者が使っていても含めない。含めると、誰が使っているかで答えが変わり、1つに決まらないためである。
- 気づけるかは、起きたときに気づけるかで決める（例：エラー、テストの失敗、費用の表示、ふだんのPRのレビュー）。害を起こす機能そのものを作るPRのレビューのような、一度だけ行う確かめは数えない。一度だけの確かめは、そのあとに起きる害を見ないためである。
- 直せば害が止まるかは、直したあとに害が続くかで決める。直すまでに使った手間と費用は数えない。
- 害がまだ見えていないもの（例：確かめていないこと、決めていないこと、書き方の指摘）は、誤っていたときの害で決める。
- 回避の方法が無く、決まっている作業（例：リリースの予定、次のPR、利用者の業務）を進められないものは、表に関わらず高にする。

残すものは、優先度の高い順に並べる。いつ行うかが同じものは、高いものから行う。1つの行には同じ優先度のものだけを書き、違うものは行を分ける。1つの行に優先度の違うものがあると、行の並びで行う順を決められないためである。

中と低は、行う手間（例：直しの量、レビューの回数）と比べ、行わない案も示す。優先度を付けずに示す場面（節「人に判断を求める指摘の形」）では、「急ぐか」で答えた2つの問いと決まっている作業を止めるかの答えを、この節の表と当てはめ方の箇条書きに当てて、高、中、低のどれかを決める。行わないと人が決めたら、理由を書く。

### 残した指摘の置き場所

残す指摘は、直さない`SUGGESTION`、直さない「前から」の指摘、チケットに分けるか人が残すと決めた`MUST`、答えが出ない`QUESTION`である。PRの前に直した指摘は、どこにも書かない。直しのコミットに残るためである。比べた案は、ハーネスの[残した指摘の置き場所の判断の記録](../docs/decisions/0018-remaining-suggestion.md)に書く。

| 場面 | 置き場所 |
|---|---|
| PRを作る作業 | PRを作る前の確認で一覧を人に示し、残すと決まったものを、変更の記録の「残っていること」に書いてPRの本文へ入れる。 |
| PRの無い作業（例：`audit-security`） | 完了の報告で一覧を人に示し（節「人に判断を求める指摘の形」）、あとで行うと決まったものをチケットにする。優先度は、チケットにするときに付ける。 |
| 導入先ごとのルールに別の形を書いた導入先 | そのルールに従う。ハーネスのリポジトリの形は、`CONTRIBUTING.md`の節「残した指摘の形」に書く。 |

PRの無い作業では、人が決めたあとの報告に、行わないものと理由を書く。人が理由を言わなければ、人の判断であることを書く。

`QUESTION`は、次のように扱う。

- まず、PRを作る前に、コードや文書を確かめて答えを出す。
- 書いた本人が答えを出せない問いは、PRを作る前の確認（PRの無い作業では、完了の報告）で人に聞く。
- 人もその場で答えられない問い（例：ほかの人の確認が要る）だけを残し、この節の表の置き場所に書く。PRの本文の「残っていること」では、分け方を「今はできない」にし、誰に確かめるかを理由に書く。答えは出せるのに出していない、と読まれないためである。

分け方の「あえて残す」の条件は、[`rules/git.md`の節「PRの題と本文」](git.md#prの題と本文)に書く。

## レビューの深さ

変更を誤ったときの害で、レビューの手間を変える。深さは、変更の記録を書くエージェントが決めて、変更の記録に書く。変更の記録が無い作業（例：ほかの人のPR、`audit-security`）では、レビューする側が決めて人に示す。レビュー役は、深さを上げるよう提案できる。比べた案は、ハーネスの[レビューの深さの判断の記録](../docs/decisions/0021-review-depth.md)に書く。

| 深さ | 当てはまる変更 | レビュー役 | 見ること |
|---|---|---|---|
| 軽い | 振る舞いを変えない変更（例：コードのコメント、誤字）で、ハーネスの`rules/`、`skills/`、`agents/`、`data/`を含まないもの | 1つ | 依頼との比較、範囲、テストの弱化、事実の誤り |
| 標準 | ほかの変更 | 1つ | 当てはまる質の問い（[`rules/quality.md`の節「問い」](quality.md#問い)） |
| 深い | 誤ると気づかないうちに害が出るか戻せない変更（例：認証、決済、権限、データの移行、`main`へのpushを止めるような保護の仕組み）、影響範囲の広い変更、緊急の変更 | 1回目は2～3つ（2回目からは、直したあとの差分を見る1つ） | 当てはまる質の問いを、観点か範囲で分けた2～3つのレビュー役がそれぞれ見る（例：1つ目が堅牢性とセキュリティと異常系、2つ目がほかの観点） |

深いの2～3つは、互いの結果を見せずに独立に動かし、議論はさせない。2～3は目安で、根拠の資料は無い。

### 使用量の見込み

サブエージェント（レビュー役と並行の実装役）を同時に2つ以上動かすときに人に示す使用量の見込み（[`rules/always-read.md`の節「人に確認を求める場面」](always-read.md#人に確認を求める場面)）は、次のように立てる。

- 読むファイルの量ではなく、リクエストの回数と1回の文脈の大きさから立てる。Claude Codeは、リクエストのたびに会話の全体を送り、ツールの結果を受けるたびにリクエストを足すためである（Manage costs effectively）。1回の返事で並べて呼んだツールの結果は、1回のリクエストにまとまる。
- 見込みには、サブエージェントの数、レビューの回数、1つあたりのリクエストの回数と文脈の大きさ（トークン）を書く。比（例：「標準の深さの2倍」）だけでは基準の量がわからず、あとで使った量と比べられないためである。
- Agentのツールが返す`totalTokens`（完了の通知の`subagent_tokens`）は、そのサブエージェントの最後のリクエストの入力（キャッシュの読み取りと書き込みを含む）と出力の和で、使った量の合計ではない。使った量として報告せず、見込みでは1回の文脈の大きさの上限として使う（回数を掛けると、多めの見込みになる）。公式の文書には意味の説明が無く、サブエージェントの記録の`usage`と比べて確かめた。

## レビュー役への頼み方

別の文脈のレビューを動かすときは、機械の確認の出力を渡し、レビュー役に次のことを頼む。

- 同じ種類の誤りは、1行ずつではなく種類で指摘する（例：「出典の一文を超える文が3か所ある」）。
- 前に出した指摘を、繰り返さない。
- 「前から」の誤りを、PRが入れた誤りと分けて書く。
- 直しの差分のレビューでは、読む範囲を次のものに絞る。理由は、ハーネスの[直しの差分のレビューの範囲の判断の記録](../docs/decisions/0017-fix-diff-review-scope.md)に書く。
  - 直しの差分（直したあとの差分）と、前の回の指摘とその扱い
  - 直しの差分が書き換えた節と、差分がリンクか名前で指す節
  - 判断の基準のルール（例：`rules/review.md`、`rules/quality.md`）と出典

レビュー役の組み合わせ（モデルとeffort）は、ハーネスの[レビュー役のモデルとeffortの判断の記録](../docs/decisions/0024-review-model.md)の「標準」と「使用量に余裕があるとき」の2つである。標準は、Opusのeffort `xhigh`のレビュー役を、レビューの深さで決めた数だけ動かす形である。

- 導入先ごとのルールに組み合わせが書いてあればそれで、無ければ標準で動かす。
- 「使用量に余裕があるとき」の1回目では、全体を見るレビュー役を1つ足す。Claude Codeでは、そのレビュー役の起動のときに、モデルを`sonnet`、effortを`high`と渡す。
- すべての導入先が使う`agents/reviewer.md`の前付けの、モデルとeffortの値は変えない。起動のときの指定は、定義の値より先に当たるためである（Create custom subagentsの節「Choose a model」「Choose an effort level」）。

## レビューを終える条件

レビューで`MUST`の指摘が出たら、確かめて直し、もう一度レビューする。終える条件は、次のとおりである。回数の上限と直し方の理由は、ハーネスの[レビューの回数の判断の記録](../docs/decisions/0008-review-round-limit.md)に書く。

| 条件 | 中身 |
|---|---|
| 範囲 | 1回目は、PRの差分（[`rules/git.md`の節「手元のマージ」](git.md#手元のマージ)の向き先のブランチから、作業用のブランチの先頭までの差分）の全体をレビューする。2回目と3回目は、PRの差分の全体か直したあとの差分（直しの差分）を、4回目からは直しの差分だけをレビューする。 |
| 終える | 直前のレビュー（全体でも直しの差分でも）で、終える条件に数える`MUST`の指摘（節「ラベルの付け方」）が0件になったら終える。 |
| 回数 | 全体のレビューと直しの差分のレビューは、合わせて5回までにする。5回目で`MUST`が残れば、続けて直さずに止め、残った指摘と、選んだ直し方を人に聞く。 |
| 3回目のあと | 3回目で`MUST`が残れば、節「3回目で残った指摘の直し方」の表で原因を分けて直し方を選ぶ。 |
| 人が決めたあと | レビューを終えたか止めたあと（例：PRを作る前の確認、5回目のあと）に人が直すと決めた指摘は、直して直しの差分をレビューする。この回は5回の数に入れず、`MUST`が残れば止めて人に聞く。 |
| 直す前 | 書いた本人が`MUST`を読んで確かめ、動かせるもの（例：落ちると言われたテストのケース）は動かして確かめる。退けるときは、理由を添えて、PRを作る前の確認で人に示す。 |
| 直し方 | 指摘された1か所だけでなく、同じ種類の誤りを、対象の全体で探して直す（例：出典に書いていないことを言う文なら、出典を付けたすべての文を見る）。直しで新しい主張を足すときは、出典か実際の動きで確かめてから書く。 |
| `SUGGESTION` | 機械で確かめられるもの（例：リンク先の見出しが無い）と、ルールや原則で直し方が決まっているもの（例：1つの事実を1か所に書く）は、人に聞かずに直す。ほかは、書いた本人は直さず、PRを作る前の確認で人に示し、直すか残すかを人が決める（行「人が決めたあと」、節「残した指摘の置き場所」）。 |

`MUST`が0件の回のあとに、人に聞かずに直した`SUGGESTION`は、機械の確認だけを動かし、レビューし直さない。直し方が決まっているので新しい誤りが入りにくく、レビューし直すと、そこで出た`SUGGESTION`の直しが続くためである。

### 3回目で残った指摘の直し方

3回目のレビューで`MUST`が残ったら、指摘の原因を分け、原因ごとに次の直し方を選ぶ。範囲の外の問題を分ける理由は、ハーネスの[PRの範囲の外の`MUST`の判断の記録](../docs/decisions/0016-out-of-scope-must.md)に書く。

| 原因 | 直し方 |
|---|---|
| 直しで足した文の誤り | 足した文を戻すか、主張を減らす。 |
| 確かめていない主張 | 確かめられなければ、その主張を消す。 |
| PRの範囲の外の問題（例：設計の前提） | このPRでは直さず、チケットに分ける案にする。 |
| ほかの原因（例：もとの差分にあった誤り） | 節「レビューを終える条件」の「直し方」のとおりに直す。 |

チケットに分ける案にした`MUST`は、PRを作る前の確認のときに人に示し、このPRで直すかチケットに分けるかを、人が決める。セキュリティに関わるものは、ほかの残りと分けて先頭に示す。

## ほかの人のPR

ほかの人のPRも、[`rules/quality.md`](quality.md)の問いで見る。

- 依頼は、PRの本文とチケットの項目がすべて入っていて、頼まれていない動きを足していないかで見る。
- 設計、複雑さ、周りのコードの問題は、変更の質の問題なので`SUGGESTION`にする。変更の周りのコードも含めて全体が良くなるかも見る。
- 名前は、[`rules/writing.md`の節「名前の具体性」](writing.md#名前の具体性)で見て、`SUGGESTION`にする。
- 良いと思った所は、`NICE`で伝える。
- セキュリティを詳しく見るときは、`audit-security`（セキュリティの確認）のスキルを使う。
