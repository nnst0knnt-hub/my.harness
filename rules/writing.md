# 文章の書き方

文章、Markdown、名前（例：ファイル、変数、ブランチ）、人に向けた書き方のルールである。エージェントは、文章を書く前にこのファイルを読む。対象は、文章を書くすべての場所である。導入先に同じことのルールや既存の形があれば、そちらに従う（[`rules/always-read.md`の節「導入先で書き方を決める順」](always-read.md#導入先で書き方を決める順)）。

規則は、誰が確かめるかで3つに分ける。理由は、ハーネスの[書き方の規則を3つに分ける判断の記録](../docs/decisions/0020-writing-rule-split.md)（ほかの案と比べて選んだ判断と理由の文書）に書く。

| 種類 | 誰が確かめるか |
|---|---|
| 分かりやすさ | 書く人が確かめ、一部の基準は止める語の一覧、確かめる語の一覧とスクリプトも確かめる（節「読みやすさ」の表）。レビューは、読み手が事実を誤って読む所だけを指摘する。 |
| 機械で止める規則 | スクリプトが確かめる。レビュー役は、スクリプトの出力があるかだけを見る。 |
| 機械で止めない形 | 書く人が確かめ、レビューは見ない。人の指摘が繰り返されたらエージェントが機械で止める側へ移し、ハーネスのリポジトリだけでスクリプトが止める規則（例：節「バッククォート」、節「数字と記号」の波形のダッシュと、6語の長音の抜け）もある。 |

人が指摘した語（例：気になった語、伝わりにくい語）は、エージェントが語の一覧へ足す（`add-rule`）。

- その導入先だけで使わない語は、導入先ごとの語の一覧（メインの作業フォルダーの`.harness/rules/word-list.txt`）へ足す。
- どの導入先でも使わない語は、ハーネスのリポジトリの変更として足す。ほかの意味で使う場面がほぼ無い語は止める語の一覧（`data/banned-word-list.txt`）へ、正しい使い方もある語は確かめる語の一覧（`data/ambiguous-word-list.txt`）へ足す。
- ハーネスのリポジトリのほかの導入先で指摘された語は、ハーネスのリポジトリの変更を待たずに、導入先ごとの語の一覧にも足す。

止める語と確かめる語の違いと理由は、節「機械で止める規則」の最後に書く。

## 分かりやすさ

### 読みやすさ

読みやすさは、想定した読み手が、初めて読んで読み返さずに、何の話か、何をするか、なぜかを読み取り、次に何をするかを決められることである。読みにくさは、主語、指すもの、語の意味、条件を、読み手が補う量が多いことである。理由と比べた案は、ハーネスの[読みやすさの定義の判断の記録](../docs/decisions/0042-readability-definition.md)に書く。

次の基準で書く。

| 基準 | 誰が確かめるか |
|---|---|
| 段落の最初の文に要点を書き、文書の結論は最初の段落に書く。 | 書く人 |
| 1文の論点は1つにし、50～60字を超えたら区切れないかを見直す。読点は、1文に0～2個を目安にする。 | 書く人 |
| 誰が、何が、何をするかを書き、仕組みを人のように書かない（例：「フックが止める」はよく、仕組みを主語にした比喩の動詞は避ける）。 | 書く人 |
| 意味の広い和語と、作業の中で作った語は、動作か正式な名前に変える。正式な名前は、初めて出る所で説明する。 | 止める語の一覧と確かめる語の一覧と書く人 |
| 同じものは同じ名前で呼び、略さない（例：「変更の記録」を「記録」にしない）。似たもの（例：変更の記録と判断の記録）は、初めて出る所で違いを書き、そのあとも書き分ける。 | 書く人 |
| 名詞を「の」で3つ以上つながず、動詞を使った文に書き換える（例：「設定の変更の確認」を「設定を変えたかを確かめる」にする）。 | 書く人 |
| 何をするかを先に書き、理由とほかの案は後ろにまとめる。比べた案は、判断の記録に書く。 | 書く人 |
| 同じ文末と同じ書き出しを続けない。 | 書く人 |
| 表のセルは2文までにする。 | スクリプト |
| 名前を、バッククォートで囲むものと囲まないものに分ける境目（節「バッククォート」）を守る。 | 書く人（ハーネスのリポジトリでは、スクリプトも） |

語の基準（作った語を使わない、同じものを同じ名前で呼ぶ、主語を書く）は、誰が読む文書にも当てる。エージェントはルールとスキルの文体を手本として真似るので、その文体が、エージェントの返事と導入先の成果物に出るためである。構造と量は、誰が読み、誰が直すかで、優先する形を分ける。

| 種類 | 例 | 優先する形 |
|---|---|---|
| 人が読む文書 | `README.md`、手引き、PRとIssue、返事、コメント | 段落の先頭の要点、1文1論点、主語、正式な名前の短い説明 |
| エージェントが読む文書 | ルール、スキル、サブエージェントへの指示、`CLAUDE.md` | 具体的で短い指示、見出しと箇条書きでの区切り、完了の条件と見せる証拠、量の上限（例：常に読むルールの3,000字） |
| 機械が読むもの | スクリプトが読む一覧（例：`data/`の一覧） | 決めた形（例：列、区切り）と、人に向けた先頭のコメント |

### 説明してから短くする

短い文にする前に、相手に口頭で説明するつもりで書く。語を削るだけでは、意味のわからない文が残るためである。

- 読み手に理解してほしいことを、1文で決める。
- 何が起きるか、なぜか、どんな場合かを話すつもりで書いてから、重なり（同じことを2回言う所）と前置きだけを削る。条件と意味は削らない。
- 作業の中で作った言葉は、初めて出る所で説明するか、起きることで書く（例：「CIを失敗させる」）。
- 変更の報告は、変更の前と後で何が違って見えるかを、具体的な例で示す。
- 行動を促す文は肯定形にする。禁止、例外、条件は、意味が変わるので否定形のままにする。

### 詳しさ

基準は、「読み手がこれを読んで、次に何をするかを判断できるか」である。

| 書くこと | 書かないこと |
|---|---|
| 結論（最初に書く） | やり取りの名残 |
| 背景（何が困っていたか）、要求（どうなればよいか）、なぜその方法か（ほかの案を採らない理由） | コードを読めばわかること |
| 初めて出る用語、コマンド、数字の説明 | ほかの場所に書いた理由の繰り返し |
| 数や基準の理由と、目安であること、確かめていないこと | 判断に使わない情報 |

報告（例：調べた結果、レビュー役の報告）では、結論に使ったファイルごとに、全文で読んだか、一部の行か、検索だけかを書く。「無い」と結論するとき（例：記載なし、残っていない）は、探した範囲（例：フォルダー、コミットの範囲）と探した語も書く。読んでいない所と探していない所を根拠にしたように結論すると、読み手が報告から気づけないためである。

特定の状況でだけ成り立つ事実（例：導入先の業務のルール、gitのフックを足した導入先だけで働く保護）は、条件を付けて書き、どこでも成り立つ事実のように書かない。

### 書く場所

| 何を | どこに |
|---|---|
| 毎回守ること | 常に読むルール |
| 手順 | スキル |
| 設計の理由 | 設計の文書（例：導入先の`.harness/docs/`の今の説明）と判断の記録 |
| 使い方 | 手引き |
| コードのその行の理由 | コードのコメント |
| 変更の理由 | コミットメッセージ |
| 背景、要求、方法、確かめ方、残っていること（残した作業と理由） | PRの本文 |
| 問題、要望、指摘 | チケット（例：Issue、Jiraの課題） |

1つの事実と理由は、1か所にだけ書く。ほかの場所からは、リンクか名前で指す。コードのコメントからは、文書の名前と節の見出しで指す。

### 文と段落

- 3つ以上の手順か項目を並べるときは、箇条書きにする。文の中の例と括弧の中には、語を並べてよい（この節の最後の項目の「例：」の規則）。
- 1つの段落には、1つの話題だけを書く。3文までを目安にする（根拠の資料は無い）。
- 項目ごとの情報が2つ以上なら表にし、1つなら箇条書きにする。
- 括弧の中や文の中に並べたものは、すべてを並べたと読まれる。例として並べるときは「例：」を付けるか、「～のような」と書く。

### 言葉

言葉は、[`rules/always-read.md`の節「言葉の判断の基準」](always-read.md#言葉の判断の基準)の11の問いで判断する。この節の表の語と、止める語の一覧と確かめる語の一覧の語は例で、「一覧に無い語は使ってよい」ではない。人が指摘した言葉は、指摘されたときから使わない。使わない範囲は、その導入先だけと決めた語ではその導入先の中、ほかの語ではどの場面でもである。

- 読み手がエンジニアのときは、基本的な技術用語（例：コミット、ブランチ、テスト）を説明なしで使ってよい。エンジニアでない人に向けた文書や資料では、技術用語を避けるか、初めて出る所で説明する。
- ほかの専門用語は、わかりやすい説明を添えれば使ってよい。説明する対象は、コマンドとその動き、プログラムの処理やメソッド、記法（例：Markdownの`~~~`は、コードブロックの囲み）、文書やコメントに出てくる言葉や数字である。
- AIがよく使う言葉（例：止める語の一覧と確かめる語の一覧の語）、比喩、相手に伝わりにくい抽象的な単語は、説明を添えて残さず、具体的な言葉に置き換える。
- 計画のファイル、作業のメモ、エージェントの記憶（例：Claude Codeの自動の記憶）にしか無い言葉（例：作業の段階や順の番号、問いや候補に付けた記号のD1とK3）は、PR、チケット、コミットメッセージ、文書と、人への返事、質問、計画、報告に書かず、中身の名前（例：記憶の移し方）で書く。読む人は、計画のファイル、作業のメモ、記憶を読めないためである。
- 過去に書いたもの（例：マージ済みのPR、閉じたIssue）は、直さない。

次の語は正しい使い方もあり、人がまだ語の一覧へ足すよう指摘していないので、機械で止めず、書く人が確かめる。

| 種類 | 語 | 確かめること |
|---|---|---|
| 独自の言い換えになりやすい語 | 枠、往復、囲む、一式、層、倒す、重ねる、つなぐ、傾く | 辞書どおりの意味か？ |
| あいまいな量・時期・対象 | いくつか、多くの、さまざまな、早めに、適宜、適切に、など | 数・日付・対象を書けるか？ |
| 誇張と宣伝 | 非常に、大幅に、欠かせない、強力な、～を実現します、～を可能にします、担保する、最適化する、強化する | 事実で書けるか？ |
| 出典のない一般化 | 一般に、業界では | 出典を書けるか？ |
| 決まり文句 | もちろんです、まとめると、要するに、結論として | 削っても意味が変わらないか？ |
| 中身の無い動詞 | 改善する、整理する、対応する、修正する | 何をどうしたかを書けるか（例：「～の条件を～に変える」）？ |

材料、仕組み、詰めるは、辞書どおりの意味で使ってよい。壁打ち（考えを話して、相手の反応で詰めること）は人とのやり取りだけで使い、文書では「議論する」と書く。

### 名前の具体性

- 名前には、動作と対象を入れる。
- 動作は、結果がわかる動詞にする（例：`find`、`deny`、`count`、`classify`、`read`、`print`）。
- `check`、`handle`、`process`、`manage`、`run`、`do`、確認、処理を、単独で使わない。
- 判定の基準は、「名前だけで、何を受け取り何をするかを1文で言えるか」である。
- 何のためかは名前に入れず、ファイルの先頭のコメントに書く。同じスクリプトを複数の目的で使うと、名前が合わなくなるためである。
- 自前の名前（例：ファイル、変数、関数、ブランチ）に省略形（例：`msg`、`cfg`）を使わない。ツールや仕様が決めた名前（例：gitの`commit-msg`）と、略語のほうが通じる語（例：PR、CI、URL）は除く。

例は、`classify-remote-command.sh`、`find-secret-in-commit.sh`、関数の`is_protected_branch`である。

### 人に向けた書き方

返事、PRとIssueの本文、レビューのコメント、チャットのような、ほかの人に向けたやり取りの全般で、次のことを守る。

- 相手に理由があったと考えて読み、人についてではなくコードについて書く。
- 理由と、どうすればよいかを書く。自分の読み違いの可能性と、確かめていないことも書く。
- 良いと思った所は、具体的に、本心から書く。
- 強い言葉、誇張、皮肉、「単に」を使わない。
- コメントのやり取りで結論が出なければ会話で話し、結果をコメントに残す。質問への返事は、お礼から書く。
- 一人称は「自分」、意見は「～と思いました」を既定にし、判断を相手にゆだねる言い方を使う（例：「～はどうでしょうか？」）。
- 人の名前で出す文（例：人のアカウントで送るレビューのコメント）は、その人の普段の書き方に合わせる。段落は、結論、理由、依頼で分ける。
- 確かめたときは、手順と結果を書く。画面の変更は、人がスクリーンショットか動画を添える。
- 絵文字は、コメントとチャットだけで、1つのコメントに1つまでを文の最後に添える（目安で、多すぎると読みにくいため）。

## 機械で止める規則

文章を書いたら、次のスクリプトを動かして出力を示す。ハーネスのリポジトリでは、CIでも動く。導入先での動かし方は、[`rules/always-read.md`の節「書く前に読むファイル」](always-read.md#書く前に読むファイル)に書く。

| 規則 | スクリプト |
|---|---|
| 止める語（`data/banned-word-list.txt`）を使わない。 | `scripts/find-banned-word.sh` |
| 確かめる語（`data/ambiguous-word-list.txt`）は、ハーネスのリポジトリと、導入先で禁止にすると答えた語では使わない。ほかでは、業務の言葉か導入先の表記の決めのときだけ使う。 | `scripts/find-banned-word.sh` |
| 導入先ごとの語の一覧（メインの作業フォルダーの`.harness/rules/word-list.txt`）の`banned`の語は、その導入先で使わない。 | `scripts/find-banned-word.sh` |
| 半角と全角の間に空白を入れない。 | `scripts/find-notation-error.sh` |
| Markdownの文書では、URLをMarkdownのリンクで書き、絵文字を使わない。 | `scripts/find-notation-error.sh` |
| 見出しに番号を付けず、`#`は1ファイルに1つ、深さは`###`までにして、段を飛ばさない（例：`#`の次に`###`を置かない）。 | `scripts/find-markdown-block-error.sh` |
| コードブロックには言語を指定し（無ければ`text`）、閉じる。YAMLの前付け（ファイルの先頭の`---`で囲んだ設定）を閉じ、値の途中に「 #」を書くときは、値を`"`で囲む。 | `scripts/find-markdown-block-error.sh` |
| 1つの箇条書きと表の1列の中で、語句と文を混ぜない。文には「。」を付け、語句には付けない。 | `scripts/find-list-and-table-error.sh` |
| 最上位の箇条書きは3項目以上にする（入れ子と出典の一覧を除く）。 | `scripts/find-list-and-table-error.sh` |
| 表のセルは2文までにする（「。」と「？」の数で数え、かぎ括弧の中は数えない）。 | `scripts/find-long-table-cell.sh` |
| 表のセルと箇条書きの項目では、文のあとに語句を続けず、最後を「。」か「？」にするか、「。」の無い1つの語句にする（かぎ括弧とインラインのコードの中の「。」は数えない）。 | `scripts/find-phrase-after-sentence.sh` |

止める語には、ほかの意味で使う場面がほぼ無い語だけを入れる。正しい使い方もある語を止めると、誤検知が増えて、確認が形だけになるためである。

人が指摘した語のうち、正しい使い方もある語は、確かめる語の一覧に入れる。スクリプトは、確かめる語を、動かした場所で次のように扱う。導入したリポジトリは、メインの作業フォルダーに`.harness/rules/`のフォルダーがあるリポジトリである。

| 場所 | 確かめる語の扱い |
|---|---|
| ハーネスのリポジトリ（worktreeを含む） | すべて止める。 |
| 導入したリポジトリ | 導入先ごとの語の一覧で禁止にすると答えた語は止め、禁止にしないと答えた語は示す。答えの無い語（決まっていない語）は、禁止にするかが決まっていないと示し、止めない。 |
| 導入していないリポジトリ、gitの外 | 示すだけで、止めない。 |

ハーネスのリポジトリで止めるのは、ルールとスキルの文体が、エージェントの返事と導入先の成果物に移るためである。導入先で一律に止めないのは、導入先の業務の言葉（例：契約、不動産、書籍の業務の用語）と表記の決めを、言い換えさせないためである。示された語は、書く人が業務の言葉か導入先の表記の決めかを見て決める。比べた案は、ハーネスの[確かめる語を場所で分ける判断の記録](../docs/decisions/0044-ambiguous-word-by-location.md)に書く。

決まっていない語が出ても、作業は止めない。エージェントは、作業の区切りで、決まっていない語をまとめて人に「この導入先でも禁止にしますか？」と聞く。

- 区切りは、`implement-change`ではPRを作る前の確認、ほかの作業では完了の報告である。PRの前に聞くのは、禁止にすると決まった語を、PRの前に言い換えるためである。
- 人が依頼で指定した文の決まっていない語は、`propose-change`が、変更の記録の承認で聞く（ハーネスの`skills/propose-change/SKILL.md`の節「変更の記録の書き方」）。
- 人が答えた語だけを導入先ごとの語の一覧に書き、答えなかった語は次の区切りでまた聞く。答えの無い語を、人が決めたこととして残さないためである。
- 導入のときは、`configure-repository`が、確かめる語ごとの表で1回聞く。

答えの書き方は、ハーネスの`skills/add-rule/SKILL.md`の節「導入先ごとの語の一覧の書き方」に書く。導入先ごとの語の一覧を読む条件と、ハーネスがパターンを変えたときの扱いは、ハーネスのリポジトリの`.harness/docs/features/harness-folder.md`の節「導入先ごとの語の一覧」に書く。

## 機械で止めない形

### 文体と言語

1つの文書の中で、敬体と常体を混ぜない。箇条書きと表のセルは、敬体の文書でも常体でよい。

- 特定の人に向けた文は敬体にする（返事、PRとIssueの本文とコメント、エラーメッセージとスクリプトが人に出す知らせ、人が読む手引き、`README.md`）。
- 定めや記録の文は常体にする（ルール、スキル、サブエージェントへの指示、要求と要件と設計の文書、判断の記録、コードのコメント、コミットメッセージ、テストの説明の文）。
- 返事と人に向けた文は、人が依頼に使った言語で書き、完了の報告と計画の要約でも変えない。
- 識別子（例：ファイル、変数、ブランチ、CIのジョブのid、設定のキー、コミットのプレフィックス）は英語にし、人が読む文と表示名（例：コミットの要約、CIの`name`、ラベル、スキルの`description`）は日本語にする。レビューのコメントのラベル5つ（`MUST`、`SUGGESTION`、`QUESTION`、`FYI`、`NICE`）は英語にする。

### 句読点

述語で終わる文には「。」を付け、名詞で終わる語句には付けない。

| 場面 | 規則 |
|---|---|
| 本文 | 体言止めにしない。 |
| 形式名詞（例：こと、もの、とき）で終わる項目 | 名詞として扱い、「。」を付けない。 |
| 括弧の中 | 語句だけを書き、「。」を付けない。文になるなら、括弧の外に出す。 |
| 引用の終わり | 最後の「。」を付けない。英語の引用は原文のままにし、最後の「.」も残す。 |
| 引用の中の強調と長さ | 強調の記号（`*`、`_`）は外す。2文以上は、引用のブロックにする。 |
| 閉じ括弧のあと | 文の「。」は、閉じ括弧の外に付ける。 |
| 見出し、題、コミットの1行目 | 「。」を付けない。 |
| 一覧や表を導く文 | 「。」で終える。 |
| 疑問と感嘆 | 疑問は「？」で書く。「！」は使わない。 |
| コメント、エラーメッセージ、`description` | 表の1行目の本文と同じ規則で書く。 |

### 数字と記号

| 対象 | 書き方 |
|---|---|
| 数えるもの | 半角の算用数字（例：1つ、3回） |
| 熟語 | 漢数字（例：一度、一部） |
| 4桁以上の数 | 3桁ごとのカンマ（例：1,000）、コードの値とバージョンと年と番号は対象外 |
| 日付と時刻 | YYYY-MM-DD（例：2026-10-22）、24時間制とタイムゾーン（例：14:30 JST） |
| 範囲と省略、割合 | 全角の「～」（U+FF5E、例：1～3）、全角の「％」 |
| カタカナ語の語尾の長音 | 省かない形（例：コンテナー、ヘッダー） |

### 見出しと箇条書き

- 見出しには、内容の中心を端的に書く。手順の見出しは「～する」、ほかは名詞にする。
- 見出しだけの節と、1行の語句を見出しの代わりに置いた所を作らない。
- 箇条書きの入れ子は、2段までにする（目安で、根拠の資料は無い）。番号付きの箇条書きは、順序に意味があるときだけ使う。1列の表は、箇条書きにする。

### バッククォート

基準は、「その文字列を、そのままコマンドや設定のファイルやコードに書くか」である。

囲むものは、コマンドと引数、ファイルとパス、設定のキーと値、イベントの名前（例：`SessionStart`）、スキルとサブエージェントの名前（例：`propose-change`）、gitのフックの名前（例：`pre-push`）、ブランチ名、環境変数、関数、変数と、名前の一部に使う英語の語（例：`find`、`utils`）である。囲まないものは、製品やサービスの名前（例：Git、bash 3.2、ShellCheck）、概念の語、URLである。

- 製品やツールの名前と同じ綴りの名前は、使い方で分ける（例：pre-commitのフレームワークは囲まず、gitのフックの`pre-commit`は囲む）。
- 文の中で製品の名前として書くときは囲まず、コマンドとして書くときは囲む（例：gitの設定、`git push`）。
- ハーネスのリポジトリでは、`linters/find-missing-backquote.sh`が、`data/backquote-name-list.txt`の名前を囲まずに書いた所を止める。

### リンクと出典

- URLをMarkdownのリンクにするのは、URLの直後の日本語がGitHub Flavored Markdownの自動のリンクに入るためである。Markdownが表示されない場所（例：コミットメッセージ、ターミナル）では、URLを行の最後に置く。
- リンクの文は、ページかファイルの名前にする。「こちら」は使わない。
- リポジトリの中のファイルは、相対パスで指す。
- 検索の結果の要約しか読んでいないページは、出典にしない。

出典は、人がページ内検索で確かめられる形で、次のように書く。

```text
[ページの名前](URL)の節「見出し」：「原文の一文」（確かめた日：YYYY-MM-DD）
```

### 改行と太字

- 段落の途中で改行しない。GitHubは、`.md`のファイルでは行をつなぎ、IssueとPRでは改行のまま表示するためである。コミットの本文とコメントでも、段落の途中で改行しない。
- 段落は空行で分ける。行末の空白2つと、`\`による改行は使わない。
- 太字は、段落の頭の小さな見出しと注意の書き出しだけに使い、箇条書きの頭に置かない。太字の中を「。」「：」「）」のような記号で終えない。CommonMarkの強調の規則で太字にならないためである。
- 斜体は使わない。
