# gitとGitHubとGitLabのルール

コミット、ブランチ、手元のマージ、PR、チケットの書き方と、PRを送るホストの決め方のルールである。このルールとスキルの「PR」は、GitLabのMR（マージリクエスト）も指す。エージェントは、コミット、ブランチ、PR、チケットを書く前にこのファイルを読む。導入先に同じことのルールや既存の形があれば、そちらに従う（[`rules/always-read.md`の節「導入先で書き方を決める順」](always-read.md#導入先で書き方を決める順)）。

## 下書きの置き場所と確かめ方

コミットメッセージ、PRの本文、チケットの本文、コメントは、次の順に書く。

1. 下書きをファイルに書く。
2. ハーネスの`scripts/find-banned-word.sh`で、機械で止める語を探す。
3. コミットメッセージは、下書きのファイルを`git commit -F`に渡す。ほかは、下書きの中身を、`gh`か`glab`のコマンドの値にそのまま書く（例：`gh pr create --title <題> --body '<本文>' --base <向き先のブランチ>`）。

止める語をコミットしたあとに見つけると、履歴を書き直すことになるためである。

`gh`と`glab`に本文を渡すときは、次のようにする。

- 本文をファイルから読むオプション（例：`--body-file`、`--description-file`、`gh api`の`--input`と`-F <名前>=@<ファイル>`）を使わない。外で動く`gh`と`glab`は、判定のあとに書き換えたファイルや、シンボリックリンクの先のファイルも読んで送り、人が確認で見るのはファイルのパスだけなので、ハーネスの判定のスクリプトが止める。
- 本文の`'`は、`'"'"'`と書く。判定のスクリプトは引用符の外の`\`を止めるので、`'\''`は使わない。
- `gh api`では、文字の値を`-f`で書き、配列の中のオブジェクト（例：`comments[][line]`）は、すべて`-F`で書く。ghは`-f`の値をすべて組んでから`-F`の値を組むので、配列の中で混ぜると、値が別のオブジェクトに付くためである。
- `-F`の値では、ghが`:owner`、`:repo`、`:branch`、`{owner}`、`{repo}`、`{branch}`を今のリポジトリの値に置き換えるので、言い換える（例：`<repo>`）。判定のスクリプトは、この語を含む`-F`の値を止める。
- GitLabに送る本文では、行の頭に`/`を書かない。GitLabが、行の頭の`/`で始まる語（例：`/merge`）をクイックアクション（承認やマージのような操作の命令）として動かすので、判定のスクリプトが止める。その語は、バッククォートで囲むか、行の頭を変える。

下書きは、一時の場所（例：Claude Codeのセッションのscratchpad、無ければ`mktemp -d`のフォルダー）に書く。コマンドが通ったら、ファイルを消す。作業フォルダーに置くと、コミットに入るおそれがあるためである。コマンドが失敗したときは、人に示すために残す。

## コミットの粒度

- 1つのコミットは、1つの論理的な変更にする。
- テストは、確かめるコードと同じコミットに入れる。
- リファクタリングは、機能の追加や不具合の修正と別のコミットにし、できれば別のPRにする。
- PRは、1つのまとまった変更にする。差分100行が目安で、1,000行は大きすぎる（Small CLsの節「What is Small?」）。差分の行数は、機械では確かめない。
- レビューや人の指摘で直したときは、前のコミットに`--amend`でまとめず、新しいコミットとして積む。pushの前でも同じで、直しをコミットごとにたどれるようにするためである。
- 人がコミットをまとめるよう頼んだときは、まとめる（例：`git commit --amend`）。まとめたほうがよさそうなときは、自分で決めずに人に聞く。

## コミットメッセージ

1行目の頭の`feat: `の部分を、「プレフィックス」と呼ぶ。「型」は、データ型と読み違えるので使わない。

プレフィックスは、Conventional Commits 1.0.0の形で、次の8つにする。

| プレフィックス | 使う場面 |
|---|---|
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | 文書だけの変更 |
| `refactor` | 振る舞いを変えないコードの変更 |
| `test` | テストだけの変更 |
| `perf` | 性能の改善 |
| `ci` | CIの設定の変更 |
| `chore` | ほかの変更（例：依存の更新、設定の変更） |

`build`と`style`は使わない。`feat(api):`の括弧の部分も使わない。

1行目は、次の形にする。

- プレフィックスを含めて50字以内（字数で数える目安で、git-commitの「no more than 50 characters」から）
- 1文で「～する」の形
- 「。」なし
- レビューの何回目か、番号だけの参照、「レビューの指摘」を書かない形

本文は、次のように書く。

- 1行空けてから書く。
- 「背景：」「要求：」「方法：」の段落で書く。背景は何が困っていたか、要求はどうなればよいかである。
- 「方法：」には、ほかの案を採らない理由も書く。
- 互換性を壊す変更は、`feat!:`と、本文の`BREAKING CHANGE:`で示す。
- チケットの参照の形は、導入先に従う。

ハーネスのリポジトリでの例は、次のとおりである。

```text
fix: 作業用のブランチへのforce pushで確認を求める

背景：force pushをふつうのpushと同じに扱い、確認なしで通していた。

要求：リモートの履歴を上書きする操作の前に、人に確認を求める。

方法：判定のスクリプトで、--forceと--force-with-leaseを見つけたら確認を求める。引数を細かく解析する案は、書き方の数だけ回避方法が出るので採らない。

Refs #12
```

## ブランチ名

- 形は、`<プレフィックス>/<何を変えるか>`にする（例：`fix/login-timeout`）。
- 英小文字、数字、ハイフンと、区切りの`/`だけを使う。
- 周回、`round2`、日付を入れない。

## 手元のマージ

向き先のブランチは、作業用のブランチのPRをマージする先のブランチである。導入先ごとのルールに書いたブランチ（向き先が複数ある導入先では、書いた選び方で決めたブランチ）にし、無ければ`main`にする。ほかの人のPR（例：`review-pr`、`audit-security`で見るPR）では、PRに書かれた向き先（GitHubの`baseRefName`、GitLabの`target_branch`）である。コマンドの`<向き先のブランチ>`は、そのブランチの名前に読み替える。

| 場面 | すること | 理由 |
|---|---|---|
| 向き先のブランチを最新にする | `git fetch origin <向き先のブランチ>`のあと、`git merge --ff-only origin/<向き先のブランチ>`で取り込む。失敗したら止めて、人に示す。 | 向き先のブランチに、手元だけのマージコミットを作らないため |
| 作業用のブランチを切る | `git fetch origin <向き先のブランチ>`のあと、`origin/<向き先のブランチ>`から切る。 | 手元の向き先のブランチが古いと、すでに入った変更を含まないブランチになり、あとで衝突と取り込みが増えるため |
| pushの前に取り込む | `git rebase origin/<向き先のブランチ>`で取り込む。 | まだ誰にも見せていない履歴で、書き換えてよいため |
| pushのあとに取り込む | `git merge origin/<向き先のブランチ>`で取り込む。 | 公開した履歴を書き換えないため |
| ほかの作業用のブランチ | 取り込まない。 | 関係のない変更が混ざるため |

向き先のブランチを取り込むのは、衝突したときと、向き先のブランチの変更が要るとき（例：並行で進めている作業の、先のPRがマージされた）だけにする。

`git pull`は使わない。ハーネスの判定のスクリプト（`git push`、`git fetch`、`git pull`、`gh`、`glab`を判定するスクリプト）が、サンドボックスの外で作業フォルダーを書き換える`git pull`を止めるためである。詳しくは、ハーネスのリポジトリの`.harness/docs/features/protection.md`の節「判定のスクリプト」に書く。

## ホストの種類

PRとチケットのコマンド（GitHubの`gh`か、GitLabの`glab`）は、PRを送るリモート（多くは`origin`）のURLのホストで、次のように選ぶ。

| ホスト | 種類 |
|---|---|
| `github.com` | GitHub |
| `gitlab.com` | GitLab |
| ほかのホスト（例：自前のGitLab、`git@github-work:`のようなSSHの別名） | 導入先ごとのルールに書いた種類 |

- 導入先ごとのルールに種類が無ければ、人に聞く。人が答えた種類は、導入先ごとのルールに書くかを聞いてから書く。
- URLのホストで決めるのは、多くの導入先で設定が要らないためである。自前のホストとSSHの別名は、URLから種類を決められないので、人が決める。
- GitLabのコマンドでは、プロジェクトをパスで書く（`glab api`では`projects/<グループ>%2F<プロジェクト>/`、ほかのコマンドでは`-R <グループ>/<プロジェクト>`）。リモートが複数（例：`origin`と`upstream`）でも、`glab`がどちらを選ぶかに依らず、確認で人が送り先を見られるためである。
- 種類の決め方の比べた案は、ハーネスの[GitHubとGitLabの導入先を同じスキルと判定で扱う判断の記録](../docs/decisions/0046-gitlab-support.md)に書く。

## PRの題と本文

- 題は、コミットの1行目と同じ規則で書く。
- 導入先にPRのテンプレートがあれば、その見出しで書く。
- エージェントは本文を値で渡すので、テンプレートが自動では入らない。ghとglabの`--template`は本文の値と一緒に使えないので、テンプレートのファイルを読み、その見出しで書く。

PRは、ホストの種類ごとに次のように作る。

| 種類 | 作り方 | テンプレート |
|---|---|---|
| GitHub | `gh pr create --title <題> --body '<本文>' --base <向き先のブランチ>`で作る。 | 導入先のPRのテンプレート（例：`.github/pull_request_template.md`）を読む。 |
| GitLab | 先に`git push`で送り、`glab mr create --source-branch <ブランチ> -R <グループ>/<プロジェクト> --title <題> --description '<本文>' --target-branch <向き先のブランチ> --yes`で作る。`--source-branch`はコマンドの名前のすぐ後ろに書き、`--fill`と`--push`は付けない。 | 既定のブランチの`.gitlab/merge_request_templates/`の`.md`のファイルを読む。複数あれば`Default.md`（大文字と小文字を区別しない）を使い、無ければどれを使うかを人に聞く。 |

GitLabで先に`git push`で送るのは、pushが判定のスクリプト（保護するブランチ、CIの設定のファイルの確かめ）を通るためである。`glab`の`--fill`と`--push`は`glab`の中でpushを動かし、`--source-branch`が後ろにあると、判定のスクリプトがほかのオプションの値と読み違えるので、判定のスクリプトが止める。

GitHubで`--base`を書くのは、書かないと`gh pr create`が、ブランチの`gh-merge-base`の設定か、既定のブランチへPRを作るためである（gh pr create）。既定のブランチと向き先のブランチが違う導入先で、別のブランチへのPRになる。

本文には、次の5つを書く。

| 内容 | 書くこと |
|---|---|
| 背景 | 何が困っていたか |
| 要求 | どうなればよいか |
| 方法 | 何をどう変えたか、ほかの案を採らない理由 |
| 確かめ方 | 何を、どう確かめたか、結果の表 |
| 残っていること | 残っていること、優先度、分け方（あえて残す、今はできない）、理由、いつ行うかの表 |

確かめ方は、次のように書く。

- 1つの表（何を、どう確かめたか、結果）にする。箇条書きと表を混ぜない。
- 行は、レビューする人が判断に使うものだけにする。
- 別の文脈のレビューは、すべての回をまとめて1行にする。どう確かめたかには、レビューの深さ（[`rules/review.md`の節「レビューの深さ」](review.md#レビューの深さ)）、回数、見た範囲を書く。ラベル（例：`MUST`は、マージの前に直す指摘）の意味は、[`rules/review.md`の節「レビューのコメント」](review.md#レビューのコメント)に書く。結果には、全回の`MUST`の合計、最後の回の`MUST`、残した数を書く（例：`MUST`は合計5件で最後の回は0件、残した指摘は1件）。残した数は、直さずに残した指摘と、答えが出ずに残した`QUESTION`の数である。
- コマンドの出力は、表の下に`<details>`で折りたたんで置く。
- 画面の変更は、人がスクリーンショットか動画を添える（[`rules/writing.md`の節「人に向けた書き方」](writing.md#人に向けた書き方)）。

残っていることは、次のように書く。

- 分け方は、「あえて残す」「今はできない」の2つにする。
- 「あえて残す」は、行えるが行わないと決めたものである。理由には、人の判断であること、弱点を受け入れた理由、このPRが入れていない誤りであることのどれかを書く。
- できたのにしていないことは、PRの前に無くす。行うか、人に聞く。人が残すと決めたら「あえて残す」にする。
- 確かめていないこと、方法の弱点、レビューの指摘で直さなかったものも、ここに書く。
- PRの前に確かめられないものは、分け方を「今はできない」にする。確かめられたのに確かめていない、と読まれないためである。
- 確かめていないことの行では、理由の列に、確かめられない理由、誰が確かめるか、それまでの扱いを書き、いつ行うかの列に、確かめる時期を書く。「誰が確かめるか」と「それまでの扱い」の列を足さないのは、確かめていないこと以外の行で空の列になり、PRのテンプレートの列も変わるためである。
- 優先度は、[`rules/review.md`の節「優先度の決め方」](review.md#優先度の決め方)のとおりに決める。
- 残っていることが無ければ、「なし」と書く。

本文には、次のものを書かない。

- 表の形の説明
- ラベルと優先度の意味
- 「指摘はすべて直した」のような文
- エージェントの帰属の行（例：「Generated with」の行）
- エージェントの使用量（例：トークンの数、金額）

帰属の行を書かない理由は2つある。エージェントが書いたことは、コミットの`Co-Authored-By`の行に残る。帰属の行の絵文字は、表記の確認（`scripts/find-notation-error.sh`）に毎回当たる。使用量を書かないのは、レビューする人がマージを決めるのに使わないためである。

レビューの指摘のうち、直さなかった指摘と、答えが出なかった`QUESTION`だけを、残っていることに書く。

## チケットの題と本文

Issue、Jiraの課題のような、問題や要望を書くものを「チケット」と呼ぶ。参照の形（例：`#12`、`PROJ-12`）は、導入先に従う。

- 題は、何が、どの条件で、どうなるかを1文で書く。
- 不具合や要望のような分類の語は、題に入れず、ラベルで付ける。
- 本文は、次の表の「本文に書くこと」の列の項目を見出しにして書く。

| 種類 | 本文に書くこと |
|---|---|
| 不具合 | 起きたこと、期待すること、再現の手順、環境 |
| 要望と指摘 | 背景、要求、案 |

## 出典

- [git-commit](https://git-scm.com/docs/git-commit)の節「DISCUSSION」：「begin the commit message with a single short (no more than 50 characters) line summarizing the change, followed by a blank line and then a more thorough description.」（確かめた日：2026-10-23）
- [Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)の節「What is Small?」：「100 lines is usually a reasonable size for a CL, and 1000 lines is usually too large」（確かめた日：2026-10-23）
- [cli/cli](https://github.com/cli/cli)のソース`pkg/cmd/pr/create/create.go`：「`--template` is not supported when using `--body` or `--body-file`」（確かめた日：2026-10-23）
- [gh pr create](https://cli.github.com/manual/gh_pr_create)：「If not provided, the value of `gh-merge-base` git branch config will be used.」、「If not configured, the repository's default branch will be used.」（確かめた日：2026-11-23）
- [gitlab-org/cli](https://gitlab.com/gitlab-org/cli)のソース`internal/commands/mr/create/mr_create.go`：「mrCreateCmd.MarkFlagsMutuallyExclusive("template", "description")」（確かめた日：2026-11-20）
- [Description templates](https://docs.gitlab.com/user/project/description_templates/)の節「Description templates」：「Present on the default branch.」、節「Set a default template for merge requests and issues」：「named `Default.md` (case-insensitive) and save it in `.gitlab/merge_request_templates/`.」（確かめた日：2026-11-20）
- [Notes API](https://docs.gitlab.com/api/notes/)：「Runs and then removes any quick actions」（確かめた日：2026-11-19）
