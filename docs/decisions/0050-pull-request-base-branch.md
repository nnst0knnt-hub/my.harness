# PRの向き先のブランチを、導入先ごとのルールに書く

| 項目 | 内容 |
|---|---|
| 状態 | 採った |
| 決めた日 | 2026-11-23 |
| 関わる設計 | [`rules/git.md`の節「手元のマージ」](../../rules/git.md#手元のマージ)、[`features/skill.md`の節「業務のルール」](../../.harness/docs/features/skill.md#業務のルール) |
| 語の意味 | [`.harness/docs/ubiquitous-language.md`](../../.harness/docs/ubiquitous-language.md) |

## 背景

- PRの向き先が`main`でない導入先と、既定のブランチとPRの向き先が違う導入先がある（例：既定のブランチが`main`で、チームの文書がPRを`develop`へ送ると決めた導入先）。
- 作業用のブランチを`origin/main`から切ると、向き先のブランチに入った変更を含まない。`implement-change`が今の説明の「確かめたコミット」を`origin/main`から辿れるかで選ぶと、変更を含まないコミットを書き、あとの`git diff`が黙って誤る。
- `gh pr create`は、`--base`が無いと、ブランチの`gh-merge-base`の設定か、既定のブランチへPRを作る。

## 判断

`configure-repository`が、既定のブランチとチームの文書を読み、PRの向き先が`main`でなければ、導入先ごとのルールに1行書く。ハーネスのルールとスキルは、向き先を「向き先のブランチ（導入先ごとのルールに無ければ`main`）」と書き、コマンドでは`<向き先のブランチ>`と書く。

## 案

| 案 | 結果 | 理由 |
|---|---|---|
| 導入先ごとのルールに1行書き、ハーネスの文は「向き先のブランチ」と書く | 採った | PRを送るホストの種類と同じ形で、判定のスクリプトを変えない。導入先ごとのルールは、毎回のセッションで文脈に入る。 |
| `.harness/config`のキーにし、セッションの始めのフックが具体的なコマンドを渡す | 採らなかった | エージェントはコマンドを読み替えずに済むが、キーを読むスクリプトとテストが増える。スキルの文の`main`も、同じく書き換えが要る。 |
| `rules/git.md`に、`main`を既定のブランチに読み替える1文だけ足す | 採らなかった | 既定のブランチとPRの向き先が違う導入先で、確かめたコミットが黙って誤る形が残る。 |

## 結果と失うもの

- 向き先が`main`の導入先では、導入先ごとのルールに何も足さず、コマンドは`main`で読める。
- エージェントは、コマンドの`<向き先のブランチ>`を毎回読み替える。読み替えを誤っても、判定のスクリプトは止めない。
- 向き先が複数ある導入先（例：`hotfix/`で始まるブランチだけ`main`へ送る導入先）では、選び方の文を導入先ごとのルールに書き、エージェントがブランチごとに選ぶ。

## 見直す条件

読み替えの誤り（例：向き先が`develop`の導入先で、`origin/main`から作業用のブランチを切った）が起きたら、`.harness/config`のキーの案と比べる。
