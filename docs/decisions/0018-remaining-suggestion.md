# 残した指摘は、導入先ではPRの本文に書き、ハーネスのリポジトリでは差分へのコメントにする

| 項目 | 内容 |
|---|---|
| 状態 | 採った |
| 決めた日 | 2026-11-05 |
| 関わる設計 | [`rules/review.md`の節「残した指摘の置き場所」](../../rules/review.md#残した指摘の置き場所)、[`CONTRIBUTING.md`の節「残した指摘の形」](../../CONTRIBUTING.md#残した指摘の形) |
| 語の意味 | [`.harness/docs/ubiquitous-language.md`](../../.harness/docs/ubiquitous-language.md) |

## 背景

直し方がルールで決まっていない`SUGGESTION`を1件ずつ人に聞くと、レビューのたびに人の判断が増える。エージェントが直すと、その直しにまたレビューが要る。

## 判断

直し方が決まっていない`SUGGESTION`は、このPRでは直さずに残し、置き場所を導入先とハーネスのリポジトリで分ける。中身は、冒頭の表の「関わる設計」に書く。

## 案

### 残し方

| 案 | 結果 | 理由 |
|---|---|---|
| 直さずに残し、PRを作る前の確認で示す | 採った | 人の判断をPRを作る前の確認にまとめられ、人が直すと決めたものだけを直してレビューする。 |
| レビューのたびに1件ずつ人に聞く | 採らなかった | レビューのたびに、人の判断が増える。 |
| すべて直す | 採らなかった | 直すたびにコミットが増え、レビューが要る。 |
| 残さずに捨てる | 採らなかった | どこにも残らず、あとで直せない。 |

### ハーネスのリポジトリの形

| 案 | 結果 | 理由 |
|---|---|---|
| 差分の該当箇所へのコメントにする | 採った | 人が該当箇所を見ながら決められ、あとで行うものだけがIssueに残る。コメントはPRの下書きと一緒に示すので、人が判断する場面を増やさない。 |
| PRごと、優先度ごとのIssueにまとめる | 採らなかった | 行わないものも開いたIssueとして残り、PRごとに増える。人が決めるのがマージのあとになる。 |
| Issueを確認なしで作る | 採らなかった | 判定のスクリプトで`gh issue create`を通すことになり、[導入先ごとのハーネスの設定（`.harness/config`）は厳しくする方向にだけ足せる前提](../../.harness/docs/features/protection.md#前提)と合わない。ハーネス全体で通すと、すべての導入先に当たる。 |
| PRの本文にだけ書く | 採らなかった | あとで行うものが、マージのあとに開いた課題として一覧に出ない。 |

導入先の既定を差分へのコメントにしないのは、導入先のチームのPRにエージェントのコメントが増え、チームのやり方を変えることになるためである。

## 結果と失うもの

ハーネスのリポジトリでは、人がマージまでにPRの上で決める手間が残る。

## 見直す条件

人が差分のコメントを見ても決めにくいとわかったら、差分へのコメントにする形をやめる。役に立つとわかったら、導入先の既定にするかを決める。
