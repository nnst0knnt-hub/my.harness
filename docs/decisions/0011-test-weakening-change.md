# テストを弱める変更は、仕組みで止めず人に聞く

| 項目 | 内容 |
|---|---|
| 状態 | 採った |
| 決めた日 | 2026-10-23 |
| 関わる設計 | [`rules/always-read.md`の節「人に確認を求める場面」](../../rules/always-read.md#人に確認を求める場面)、[`features/reviewer.md`](../../.harness/docs/features/reviewer.md) |
| 語の意味 | [`.harness/docs/ubiquitous-language.md`](../../.harness/docs/ubiquitous-language.md) |

## 背景

テストを消す、スキップする、期待値を緩める変更は、常に読むルールで、人に確認を求める場面に入っている。誰がどう見つけて止めるかを決める必要がある。

## 判断

常に読むルールで、変える前に人に聞かせる。レビュー役が`MUST`で挙げる。

## 案

| 案 | 結果 | 理由 |
|---|---|---|
| 変える前に人に聞き、レビュー役が`MUST`で挙げる | 採った | エージェントとレビュー役が、文字列で判定せず、意味で判断できる。 |
| フックで見つけて止める | 採らなかった | スキップの書き方は言語やテストフレームワークごとに違い（例：`.skip(`、`xit(`、`@Disabled`、`t.Skip()`、`pytest.mark.skip`）、ハーネスが技術ごとの知識を持たないこと（[`architecture.md`の節「範囲の外」](../../.harness/docs/architecture.md#範囲の外)）と合わない。期待値を緩めたか（例：`toBe(3)`を`toBeGreaterThan(0)`に変える）は、文字列では判断できない。 |

## 結果と失うもの

秘密情報の漏れのように、仕組みで厳しく止めはしない。テストを弱める変更は差分に残り、マージの前ならレビュー役、人が行うPRのレビュー、CIで気づいて戻せるためである。
