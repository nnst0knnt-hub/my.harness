# 指摘と気づきを記録する

人の指摘と、作業中に気づいたことを、次のセッションからも守られる場所に記録する手順である。置き場所は、指摘の中身で分ける。

- 導入先（ハーネスを入れたリポジトリ）だけのことは、導入先ごとのルールに書く。導入先ごとのルールは、メインの作業フォルダー（worktreeでない元の作業フォルダー）の`.harness/rules/always-read.md`である。`SessionStart`のフックが、毎回のセッションの始めに渡す。
- どの導入先でも守ることは、ハーネスのリポジトリ（ハーネスのルール、スキル、スクリプトを置くリポジトリ）のIssueにする。手元のハーネスのリポジトリのパスは、フックが「ハーネスの場所」として渡す。
- 人が指摘した語は、導入先ごとの語の一覧（メインの作業フォルダーの`.harness/rules/word-list.txt`）に足す。どの導入先でも使わない語は、ハーネスのリポジトリのIssueにもする（節「人が指摘した語」）。
- Claude Codeの自動の記憶（Claude Codeが、PCごとに自分で書いて次のセッションで読むメモ）には、人が「覚えておいて」と頼んだときも書かない。自動の記憶はPCとリポジトリごとに保存され、ほかのPCとほかの導入先では読まれないためである（ハーネスのリポジトリの`.harness/docs/features/skill.md`）。

## 手順

1. 指摘を「どの場面で、何を、どうする」の1文にし、誰が見つけたか（人の指摘か、エージェントの気づき）を決める。1文にできなければ、人に聞く。
2. 置き場所を、節「置き場所」の表で決める。
3. 同じ指摘がすでにあるかを、節「同じ指摘を探す」のとおりに探す。
4. 置き場所、書く文（Issueなら題、本文、ラベル、優先度とその理由）、探した結果を人に示し、承認を得る。Issueなら、作るアカウントと書き込みの権限も示し、人が作り方を選ぶ（節「Issueを作るアカウント」）。
5. 承認を得たら、節「書き方」のとおりに書き、書いた場所かIssueのURLを報告する。

承認の前には、ルールもIssueも書かない。ルールの直し（`.harness/`のルールの変更）とIssue（ほかの人に見える書き込み）は、どちらも常に読むルールの節「人に確認を求める場面」に当たるためである。常に読むルールは、フックが毎回渡す、ハーネスの`rules/always-read.md`と導入先ごとのルールである。

## 置き場所

| 指摘の中身 | 置き場所 |
|---|---|
| その導入先だけのこと（例：テストの前にDockerを起動する） | 導入先ごとのルールに書く。導入先ごとのルールが中身を別のファイルに書くと決めていれば（例：ハーネスのリポジトリの`CONTRIBUTING.md`）、そのファイルに書く。 |
| どの導入先でも守ること（例：書き方、スキルの手順の抜け） | ハーネスのリポジトリのIssueにする。 |
| 人が指摘した語（例：気になった語、伝わりにくい語） | 節「人が指摘した語」のとおりに置く。この導入先だけで使わない語か、どの導入先でも使わない語かは、依頼が範囲を言っていなければ（例：「このリポジトリで」「どのリポジトリでも」）、手順4で人に聞く。 |
| モデルとeffort（例：「使用量が大きい」「精度が落ちた」） | 節「モデルとeffortの置き場所」のとおりに書く。 |

### 導入先ごとのルールに書くとき

- 導入先のチームのルール（例：`CLAUDE.md`、`CONTRIBUTING.md`）にすでに書いてあることは、導入先ごとのルールにコピーしない。チームのルールと食い違えば、食い違いを人に示す。
- 導入先ごとのルールが無ければ（メインの作業フォルダーに`.harness/`が無い）、書かずに、先に`configure-repository`で導入することを勧める。`.git/info/exclude`の設定が無いまま作ると、`.harness/`が導入先のgitに入るためである。`configure-repository`は、導入先を読んで導入の設定を書くスキルである。
- 置き場所がgitで追跡されるファイル（例：ハーネスのリポジトリの`CONTRIBUTING.md`）なら、今のブランチの変更としてコミットするか、Issueにするかを人に聞く。導入先ごとのルールが決めた置き場所への書き込みは、`configure-repository`が書く導入の設定とは違い、人が承認した導入先の変更として扱う。

### ハーネスのリポジトリに書くとき

- どの導入先でも守ることは、導入先のセッションから直接ハーネスを直さない。ハーネスの変更はすべての導入先に当たるので、ハーネスのリポジトリの手順（変更の記録、テスト、レビュー）を通すためである。変更の記録は、PRごとに背景から作業の手順までを書き、人の承認を得る文書である。
- 人が今直すと決めたら、ハーネスのリポジトリのセッションで、`propose-change`（変更の記録を書いて人の承認を得るスキル）から始めるよう伝える。
- 今のセッションがハーネスのリポジトリなら、そのまま`propose-change`を使う。ハーネスのリポジトリかは、ハーネスの`scripts/find-harness-repository.sh <メインの作業フォルダー>`を動かし、0で終われば（ハーネスのリポジトリかそのworktreeなら）ハーネスのリポジトリとする。
- スクリプトが2で終われば、どちらとも決めずに止め、標準エラーに出た文を人に示す。補助のスクリプトが欠けたときに、ハーネスのリポジトリを導入先と取り違えないためである。
- 場所の文字列をそのまま比べない。フックは、ハーネスの場所をシンボリックリンクを残したまま渡し、メインの作業フォルダーをリンクを解いて渡すので、同じリポジトリでも文字列が違うことがある。スクリプトは、リンクを解いた2つのメインの作業フォルダーを比べ、ハーネスの`scripts/`にあるので確認なしで動く。
- `.harness/`がgitで追跡されているかでは見分けない。チームで`.harness/`をコミットした導入先を、ハーネスのリポジトリと取り違えるためである。

### 人が指摘した語

人が指摘した語は、この導入先だけで使わない語か、どの導入先でも使わない語かで、置き場所を分ける。

| 指摘した語 | 置き場所 |
|---|---|
| この導入先だけで使わない語（例：業務で「顧客」と呼ぶものを指す「ユーザー」） | 導入先ごとの語の一覧に、`banned`の行を足す。 |
| どの導入先でも使わない語 | ハーネスのリポジトリのIssueにし、語の一覧に足す案を書く。導入先ごとの語の一覧にも、`banned`の行を足す。 |

- Issueの案は、ほかの意味で使う場面がほぼ無い語なら止める語の一覧（ハーネスの`data/banned-word-list.txt`）へ、正しい使い方もある語なら確かめる語の一覧（ハーネスの`data/ambiguous-word-list.txt`）へ足す案にする（ハーネスの`rules/writing.md`の、節「分かりやすさ」の前の段落）。
- 導入先ごとの語の一覧にも足すのは、ハーネスのPRがマージされるのを待たずに、次の確認からその導入先で止めるためである。
- ハーネスのリポジトリでは、導入先ごとの語の一覧を置かず、`propose-change`でハーネスの語の一覧に足す。ハーネスのリポジトリの語の確認は、導入先ごとの語の一覧を読まないためである。
- メインの作業フォルダーに`.harness/rules/`のフォルダーが無ければ、書かずに、先に`configure-repository`で導入することを勧める。理由は、節「導入先ごとのルールに書くとき」と同じである。

### モデルとeffortの置き場所

- 本体の会話（サブエージェントを起動する側の会話）のモデルとeffortは、導入先の`.claude/settings.local.json`の`model`と`effortLevel`に書く。書き方は、ハーネスの`skills/configure-repository/SKILL.md`の節「書き方」の、`.claude/settings.local.json`の行のとおりにする。
- レビュー役（`reviewer`のサブエージェント）のモデルとeffortは、レビュー役の組み合わせ（レビュー役の数と、それぞれのモデルとeffort）として、導入先ごとのルールに1行で書く。書き方は、ハーネスの`rules/review.md`の節「レビュー役への頼み方」に書く。
- レビュー役が`MUST`（マージの前に直す指摘のラベル）を見逃したなら、ハーネスのリポジトリのIssueにもする。ハーネスのレビュー役のモデルとeffortの判断の記録（`docs/decisions/0024-review-model.md`）の見直す条件（人のレビューで、`MUST`の見逃しが見つかったとき）に当たるためである。判断の記録は、ほかの案と比べて選んだ判断と理由の文書である。

## 同じ指摘を探す

- 導入先ごとのルールは、ファイルを読み、同じ場面のことが書かれていないかを見る。書かれていれば、足さずに、今の文を直す案にする。
- 人が指摘した語は、導入先ごとの語の一覧と、ハーネスの2つの語の一覧も読み、同じ語の行が無いかを見る。
- Issueは、`gh issue list -R <リポジトリ> --state all --limit 100 --search "<指摘の中心の語>"`で、閉じたものも含めて探す。語を変えて2回以上探す。`--limit`を付けるのは、既定では30件までしか読まないためである（`gh issue list --help`の`--limit`の行）。
- `<リポジトリ>`には、ハーネスの場所で`git remote get-url origin`を動かし、URLから取り出した`OWNER/REPO`の形を入れる。

同じ指摘のIssueがあれば、新しいIssueを作ってから、`gh issue close <新しい番号> -R <リポジトリ> --duplicate-of <元の番号>`で閉じる。同じ指摘が何回出たかを、ラベルの数で数えるためである（ハーネスのリポジトリの`.harness/docs/architecture.md`の節「測り方」）。

## 書き方

### 導入先ごとのルールの書き方

- 1つの規則を1文で書き、理由が要るときだけ「～ためである。」を足す。
- 書いたら、ハーネスの`rules/writing.md`の節「機械で止める規則」の表にあるスクリプト（例：止める語を探す`scripts/find-banned-word.sh`）を、すべて書いたファイルに動かす。`find-banned-word.sh`が2で終わり、標準エラーに導入先ごとの語の一覧の誤りが出たときは、ハーネスの`skills/implement-change/SKILL.md`の節「テストと文章の確認」のとおりにする。
- ハーネスの`scripts/find-long-rule.sh`でファイルの字数を数える。3,000字を超えたら、毎回守らなくてよい中身（例：手順、背景）を今の説明へ移す案を人に示し、承認を得てから移す。今の説明は、導入先の`.harness/docs/`に置く、導入先の今の状態を書く文書（例：`architecture.md`の節「前提」）である。
- 3,000字以内でも、フックの出力の合計が8,000字を超えると、フックが、導入先ごとのルールか文書の目次（`.harness/docs/README.md`）の本文を省き、場所だけを渡す。ハーネスの`skills/configure-repository/SKILL.md`の節「書いたあとの確かめ」の「フックが本文を省かない」の行のとおりに確かめ、省いていれば、その行のとおりに移す案を示す。
- 導入先ごとのルールはメインの作業フォルダーにあるので、worktreeの中で動いていても、メインの作業フォルダーのファイルを直す。

導入先ごとのルールを短く保つのは、毎回のセッションでフックが渡すためである（ハーネスのリポジトリの`.harness/docs/features/always-read-rule.md`）。

### 導入先ごとの語の一覧の書き方

導入先ごとの語の一覧は、メインの作業フォルダーの`.harness/rules/word-list.txt`である。`configure-repository`と`implement-change`も、確かめる語への答えを、この節のとおりに書く。

1行に1語を、次の3つの種類のどれかで、列をタブで区切って書く。`#`で始まる行はコメントで、改行はLFにする。

| 種類 | 列 | 意味 |
|---|---|---|
| `banned` | `banned`、パターン、代わりの言い方、除く形（任意） | この導入先だけで止める語である。列の意味は、ハーネスの`data/banned-word-list.txt`と同じである。 |
| `ambiguous-banned` | `ambiguous-banned`、確かめる語のパターン | 確かめる語を、この導入先でも禁止にする答えである。 |
| `ambiguous-allowed` | `ambiguous-allowed`、確かめる語のパターン | 確かめる語を、この導入先では禁止にしない答えである。 |

書くときは、次のことを守る。

- パターンと除く形は、`LC_ALL=C`の`grep -E`で読める形（拡張正規表現）にする。除く形は、空の文字列に当たる形（例：末尾の縦線）にしない。当たると、語の確認が誤りで止まる。
- 確かめる語への答えのパターンは、ハーネスの`data/ambiguous-word-list.txt`の1列目の文字列を、そのまま書く。スクリプトはパターンの文字列どうしを比べるので、一部だけを書いた行は答えにならない。
- 確かめる語と同じパターンの`banned`の行も、禁止にする答えとして数える。
- 同じパターンに、禁止にする答えと禁止にしない答えを両方書かない。両方あると、語の確認が誤りで止まる。答えを変えるときは、今の行を直す。
- 人が答えた語だけを書き、答えなかった語は書かない。
- ファイルが無ければ、1行目に、形を書いた場所を指すコメント（例：`# 導入先ごとの語の一覧。形は、ハーネスのskills/add-rule/SKILL.mdの節「導入先ごとの語の一覧の書き方」に書く。`）を書く。
- ファイルのツール（Claude CodeではEdit、Write）で書く。サンドボックスの中のコマンドは`.harness/rules/`に書けず、ファイルのツールでは、PCの設定のaskのルールで確認が出る。

書いたら、ハーネスの`scripts/print-project-word-list.sh <メインの作業フォルダー>/.harness/rules/word-list.txt`を動かし、0で終わることを確かめる。1で終われば、標準エラーに出た文のとおりに直す。行の誤りは「ファイル:行」の形で、ファイルの誤り（例：シンボリックリンク、読めないファイル）はファイルの名前で示される。一覧には、文章の確認（止める語と表記のスクリプト）を当てない。一覧には、語そのものが並ぶためである。

### Issueの書き方

- 題と本文は、ハーネスの`rules/git.md`の節「チケットの題と本文」で書く。本文の見出しは、要望と指摘のチケットの見出し（背景、要求、案）にする。
- 本文の下書きを、ハーネスの`rules/git.md`の節「下書きの置き場所と確かめ方」のとおりに、一時のフォルダーのファイルに書き、ハーネスの`scripts/find-banned-word.sh`を動かす。示された語は、次のように扱う。ハーネスのリポジトリの文なので、ハーネスの扱い（導入先ごとの語の一覧を読まず、確かめる語をすべて止める）にそろえるためである。
  - ハーネスの止める語と確かめる語（決まっていない語を含む）は、人に聞かずに示された代わりの言い方に変え、作業の区切りで聞く「この導入先でも禁止にしますか？」の問いにも入れない。
  - 導入先ごとの語の一覧の`banned`の行にだけある語（ハーネスの`data/banned-word-list.txt`と`data/ambiguous-word-list.txt`に同じパターンの行が無い語）は、言い換えない。同じ所にハーネスの止める語か確かめる語も示されたら（例：導入先の`banned`の熟語の一部が、ハーネスの1字の確かめる語に当たる）、上の項目のとおりに言い換える。
  - 2で終わり、標準エラーに導入先ごとの語の一覧の誤りが出たときは、ハーネスの`skills/implement-change/SKILL.md`の節「テストと文章の確認」のとおりにする。
- 言い換えたら当て直し、2で終わらず、言い換える語が残っていないことを確かめてから、`gh issue create -R <リポジトリ> --title <題> --body '<本文>' --label <ラベル>`で作る。本文には下書きの中身をそのまま書き、`'`は`'"'"'`と書く。ファイルを渡すオプション（例：`--body-file`）は、判定のスクリプトが止める（ハーネスの`rules/git.md`の節「下書きの置き場所と確かめ方」）。作ったら、下書きを消す。
- ラベルは、ハーネスの`CONTRIBUTING.md`の節「ラベル」の3種類（種類か対象、誰が見つけたか、優先度）を1つずつ付ける。優先度はハーネスの`rules/review.md`の節「優先度の決め方」で決め、理由をIssueのコメントに書く。
- 題、本文、コメントには、指摘を受けた場面（何をしていて、何が起きたか）を、どの導入先でも起きる形（例：「表の列の意味を推測で補った」）で書く。導入先の名前、業務の言葉とルール、コード、秘密情報は書かない。ハーネスのリポジトリのIssueは導入先と別の人が読み、公開のリポジトリでは誰でも読めて、消しても読まれた中身は戻らないためである。
- 保護を越える方法（例：判定のスクリプトが止めなかったコマンドの形）は、ハーネスの`skills/audit-security/SKILL.md`の節「人が決めたあと」の公開のチケットの規則に従い、Issueに書かずに置き場所を人に聞く。

`gh`が認証されていないか、GitHubのAPIが失敗した（例：403）ときは、題、本文、ラベル、コマンドを人に示し、人が作るか、認証してから続けるかを聞く。書き込みを別の方法で試さない。

### Issueを作るアカウント

手順4の承認の前に、Issueを作る`gh`のアカウントと、そのアカウントがハーネスのリポジトリに書けるかを読んで、人に示す。`<リポジトリ>`は、節「同じ指摘を探す」と同じ`OWNER/REPO`の形である。

- アカウントの名前は、`gh api user --jq .login`で読む。
- 書けるかは、`gh api repos/<リポジトリ> --jq .permissions.push`で読み、`true`なら書ける。
- どちらも読み取りで、判定のスクリプトが確認なしで通す。

読んだ結果ごとに、示すことと人が選ぶことを、次のように分ける。

| 結果 | 人に示すこと | 人が選ぶこと |
|---|---|---|
| 書ける（`true`） | アカウントの名前 | そのアカウントで作るか、題、本文、ラベルだけを受け取るか |
| 書けない（`true`でない） | アカウントの名前と、作るときに付けたラベルが黙って捨てられること（Create an issue） | そのアカウントでラベルの無いIssueを作るか、題、本文、ラベルだけを受け取るか |
| コマンドが失敗した（例：ログインしていない、`gh`が無い） | 標準エラーに出た文 | ログインしてから続けるか、題、本文、ラベルだけを受け取るか |

人が受け取るほうを選んだら、`gh issue create`を動かさず、題、本文、ラベル、優先度の理由（Issueのコメントに書く文）を返事に示す。同じ指摘のIssueがあれば、閉じるときに指す元の番号も示す。

アカウントを示すのは、書き込みの権限の無いアカウントではラベルが黙って捨てられ、「人の指摘」のラベルで数える指摘の数が黙って減るためである。権限があっても、そのPCでIssueを作ってよいアカウントかは人が決めるので、名前を示す。
