# コードを変えずに調べて報告する

依頼を問いに分け、問いごとに答えと根拠を報告する手順である。作業フォルダーのファイルは変えない。

## 手順

1. 依頼を問いに分ける（例：何が起きているか、なぜ起きるか、どこに影響するか、どう直せるか）。問いが決まらなければ、何を知りたいかを人に聞く。
2. 作業の前に、作業フォルダーで`git status --porcelain`と`git branch --show-current`を動かし、出力を控える。ブランチが変わっても、`git status --porcelain`は空のことがあるので、2つとも控える。
3. 問いごとに、節「調べ方」のとおりに調べ、主張ごとに根拠を付ける。
4. 作業の最後に、手順2の2つのコマンドをもう一度動かし、作業の前と同じであることを示す。違えば、何が変わったかを人に示し、戻すかを聞く。
5. ハーネスの`rules/quality.md`の節「案の比べ方」と、同じファイルの節「問い」の観点を読み、節「報告の形」のとおりに報告する。

完了の条件は、常に読むルール（フックが毎回渡す、ハーネスの`rules/always-read.md`と導入先ごとのルール）の節「完了の条件」のとおりである。比べる差分が無いのでレビュー役は使わず、問いごとに答えと根拠があるかを自分で見る。根拠の無い答えは、確かめるか、推測と書く。

## 調べ方

- コード、テスト、履歴（例：`git log -S <語>`、`git blame`）、導入先（ハーネスを入れたリポジトリ）のチームの文書、`.harness/docs/`の今の説明（導入先の今の状態を書く文書で、目次から選ぶもの）を読む。技術の知識は、導入先が使っているバージョンの公式の文書で確かめる。
- 広く探す所（例：名前の使われ方を、リポジトリの全体で探す）は、読み取り専用の調べ役（Claude CodeではExplore）に任せる。本体の会話（サブエージェントを起動する側の会話）の文脈に、探す途中のファイルの中身を残さないためである。結論に使う行は、調べ役の要約で済ませず、自分で読んで確かめる。
- 再現は、作業フォルダーを変えないコマンド（例：読むだけのテストの実行）か、一時のフォルダー（例：`mktemp -d`のフォルダーに作業フォルダーをコピーしたもの）で行う。テストやビルドがファイルを書く（例：キャッシュ、カバレッジ）ときは、一時のフォルダーで動かす。
- 自分で作った一時のフォルダーは、終わったら人に聞かずに消す。リポジトリのコピーだけを置いた場所で、消しても失うものが無いためである。
- 本番や共有の環境（例：本番のデータベース、共有のステージング）には触らない。そこのログやデータが要るときは、常に読むルールの節「人に確認を求める場面」の、人に作業を頼む条件（結果が成果物の精度に関わり、自分のツールでは得られず、同じ質の別の方法が無い）で人に頼む。

## 根拠の書き方

| 主張の種類 | 根拠 |
|---|---|
| コードがこう動く | `path:line`と、その行の中身 |
| 動かすとこうなる | 動かしたコマンドと出力（長ければ、要る行だけ） |
| 仕様や業務のルール | 文書の名前と節、無ければ人の回答 |
| 確かめていない | 「推測」と書き、何を見れば確かめられるかを添える |

## 報告の形

返事は、次の順に書く。

1. 結論（最初の問いの答えを1～2文で）
2. 問いごとの答えと根拠（節「根拠の書き方」の形）
3. 影響範囲（変えると動きが変わる所を、`path:line`で並べる）
4. 選択肢（案、起きること、得るものと失うもの、勧めるかの表）
5. 確かめていないこと（何を、なぜ確かめられないか、誰が確かめられるか）
6. 作業の前と後の`git status --porcelain`と今のブランチの出力

選択肢は、ハーネスの`rules/quality.md`の節「案の比べ方」のとおりに比べ、勧める案と、優先した観点と、その理由を最後に書く。

結果は`.harness/docs/`に書かない。今の説明は導入先の今の状態を書く文書で、調べた結果の置き場所ではないためである。調査の結果は、変更につながったときに、変更の記録の「調べたこと」に入れる（ハーネスのリポジトリの`.harness/docs/features/harness-folder.md`の節「書き分け」）。

人が直すことを頼んだら、`propose-change`（変更の記録を書いて人の承認を得るスキル）を使い、報告の答えと根拠を変更の記録の「調べたこと」に書く。報告を別のファイルに残すよう頼まれたときは、置き場所を人に聞く。
