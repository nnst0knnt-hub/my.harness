# 変更の記録どおりに実装してPRを作る

承認された変更の記録の作業の手順を進め、別の文脈のレビューを通してPRを作る手順である。

- 変更の記録は、導入先（ハーネスを入れたリポジトリ）の`.harness/docs/changes/`に、PRごとに1つ置く文書で、`propose-change`が書く。作業の手順は、変更の記録の節「作業の手順」のチェックボックスの一覧である。
- 別の文脈のレビューは、レビュー役（`reviewer`のサブエージェント）が、本体の会話（サブエージェントを起動する側の会話）とは別の文脈で行うレビューである。
- 手順の並びは、ハーネスのリポジトリの`.harness/docs/architecture.md`の節「依頼から完了までの流れ」の図と同じにする。
- 向き先のブランチは、作業用のブランチのPRをマージする先のブランチで、導入先ごとのルールに無ければ`main`である（ハーネスの`rules/git.md`の節「手元のマージ」）。コマンドの`<向き先のブランチ>`は、そのブランチの名前に読み替える。

## 手順

1. 変更の記録を見つけ、ブランチを切る（節「変更の記録とブランチ」）。
2. ハーネスの`rules/quality.md`を読み、作業の手順を上から進めて、終えたものにチェックを付ける。作業の手順のまとまり（見出しで分けた一続きの行）を終えたら、新しいセッションで続けるよう人に勧めるかを決める（節「セッションの分け方」）。最後に、今の説明と目次を直す（節「今の説明」）。
3. ハーネスの`rules/git.md`を読み、commitして、作業用のブランチへpushする。
4. テストとlintを動かし、文章の確認を当てる（節「テストと文章の確認」）。動かしたコマンドと出力を示し、変更の記録の節「確かめ方」の表の、結果の列を埋める。
5. 変更の記録のレビューの深さで、レビュー役に頼む（節「レビュー役に渡すもの」）。`MUST`（マージの前に直す指摘）は、ハーネスの`rules/review.md`の節「レビューを終える条件」の「直す前」の行のとおりに確かめてから直す。直しは新しいコミットとして積み、同じ節の条件を満たすまで繰り返す。
6. PRを作る前の確認として、残す候補の指摘と、退けた`MUST`を、ハーネスの`rules/review.md`の節「人に判断を求める指摘の形」で人に示す（節「残す候補の指摘」）。禁止にするかが決まっていない確かめる語が出ていれば、同じ確認でまとめて聞く（節「決まっていない語」）。
7. 変更の記録からPRの本文の下書きを作り（節「PRの本文」）、人の確認を得て、ハーネスの`rules/git.md`の節「PRの題と本文」のとおりにPRを作る。CIの結果を節「ホストごとのコマンド」のとおりに読み、落ちていれば直す。
8. 変更の記録の状態を「完了」にする（節「変更の記録を完了にする時期」）。変更の記録がgitで追跡される導入先では、手順6の確認のあと、手順7でPRを作る前に行う。

レビューの前にcommitとpushをするのは、PRに入る変更をすべてレビューに通すためである。pushでCIが動く導入先では、PRの下書きを人に示す前に、CIの結果も得られる。

### テストと文章の確認

- 導入先ごとのルール（メインの作業フォルダーの`.harness/rules/always-read.md`）に書いたテストとlintを動かす。メインの作業フォルダーは、`SessionStart`のフックが渡す、worktreeでない元の作業フォルダーである。
- 導入先ごとのルールが、人がClaude Codeの外で動かすと書いたテスト（例：手元のサーバーを使うテスト）は、動かすコマンドを人に示し、人が渡した出力を、動かしたコマンドの出力として示す。人の出力を待つ間に、ほかのテストと文章の確認を先に進める。
- 導入先ごとのルールに書いたテスト（人がClaude Codeの外で動かすものを含む）のうち、変更が当たらないと判断して動かさないもの（例：文書だけの変更での結合テスト）は、名前と動かさない理由を、ほかのテストの出力と一緒に人に示し、PRの本文の確かめ方にも書く。書かないと、レビューする人が、動かさなかったのか、忘れたのかを見分けられないためである。
- ハーネスの`scripts/`の文章の確認を、常に読むルールの節「書く前に読むファイル」のとおりに当てる。常に読むルールは、フックが毎回渡す、ハーネスの`rules/always-read.md`と導入先ごとのルールである。
- 止める語の確認（`find-banned-word.sh`）は、変えたファイルとコミットメッセージに当てる。2で終わり、標準エラーに導入先ごとの語の一覧（メインの作業フォルダーの`.harness/rules/word-list.txt`）の誤りが出たら、語を1つも探していない。ハーネスの`skills/add-rule/SKILL.md`の節「導入先ごとの語の一覧の書き方」のとおりに直す案を人に示し、直してから当て直す。
- 表記の確認は、導入先に表記のルールが無いときだけ、変えたMarkdownのファイル（例：`git diff --name-only origin/<向き先のブランチ>...HEAD -- '*.md'`の出力）に当てる。表記の確認のスクリプトはMarkdownの記法を読むので、ほかのファイルには当てない。

### 決まっていない語

決まっていない語は、導入先ごとの語の一覧（メインの作業フォルダーの`.harness/rules/word-list.txt`）に答えの無い確かめる語で、`find-banned-word.sh`が「この導入先で禁止にするかが決まっていません」と示す。確かめる語は、人が指摘した語のうち、正しい使い方もある語である。

- 示されても、作業は止めない。業務の言葉か導入先の表記の決めでなければ、示された代わりの言い方に変える。
- 示された文の「一覧のパターン」と代わりの言い方、使った場所、業務の言葉か表記の決めとして残したかを控える。
- 手順6で、パターンごとに1行の表（パターン、代わりの言い方、使った場所、勧め）にして、「この導入先でも禁止にしますか？」とまとめて聞く。勧めは、残した語なら「禁止にしない」、ほかは「禁止にする」にする。パターンの`|`は、表では`\|`と書く（ハーネスの`skills/configure-repository/SKILL.md`の節「確かめる語の表」）。
- 答えは、ハーネスの`skills/add-rule/SKILL.md`の節「導入先ごとの語の一覧の書き方」のとおりに書く。答えの無い語は書かず、次の区切りでまた聞く。
- 「答えに当たる確かめる語が、ハーネスの一覧にありません」と出たら、同じ確認で、その行を消すか、今のパターンで答え直すかを人に聞く。
- 禁止にすると決まった語が差分に残っていれば、PRを作る前に言い換えて、新しいコミットにする。

### 残す候補の指摘

残す候補の指摘は、このPRで直さずに残すかを、人に決めてもらう指摘（例：直し方がルールで決まっていない`SUGGESTION`）である。`SUGGESTION`は、直すとよいが、マージを止めない指摘のラベルである。

- 残すと決まったものは、ハーネスの`rules/review.md`の節「残した指摘の置き場所」の表のとおりに置く（既定は、変更の記録の「残っていること」）。
- 導入先ごとのルールで、残した指摘をPRへのコメントにすると決めた導入先では、コメントの最後に`<!-- my-harness -->`を付ける。エージェントが答えたか、人の判断を待つコメントに付ける、表示されないHTMLのコメントで、付け方はハーネスの`rules/review.md`の節「レビューのコメント」に書く。
- 前からの脆弱性（PRの変更より前からある脆弱性）をチケットにするときは、ハーネスの`skills/audit-security/SKILL.md`の節「人が決めたあと」の、公開のチケットの規則に従う。公開のリポジトリでは、節「公開のリポジトリの脆弱性」のとおりにも扱う。

### 公開のリポジトリの脆弱性

公開のリポジトリ（節「ホストごとのコマンド」の「公開のリポジトリか」で見る）では、レビューで見つけた前からの脆弱性の中身を、次のように扱う。中身は、脆弱性の種類、場所、攻撃のしかたで、ハーネスの`skills/audit-security/SKILL.md`の節「人が決めたあと」と同じものを指す。

- 中身を、PRの本文、残す候補のコメント、コミットメッセージ、変更の記録に書かない。人が決めた非公開の場所にだけ書き、置き場所は手順6の確認で人に聞く。
- gitで追跡されない変更の記録にも、中身を書かない。変更の記録の「残っていること」を、PRの本文へそのまま入れるためである。
- 残すと決まった脆弱性は、変更の記録、PRの本文、PRのコメントのどこに置くときも、中身の無い文（例：「前からのセキュリティの指摘（中身は非公開の場所に書いた）」）で書き、省かない。省くと、PRをレビューする人が、残したものがあると知らずにマージを決めるためである。

公開の場所に中身を書くと、直す前に中身が広まる。

### 変更の記録に無い変更

作業の手順に無い変更が要るとわかったら、進めずに人に示し、変更の記録を直して承認を得る。変更の記録に無い変更は、人が承認していないためである。

レビューの指摘で、承認された変更の記録の文を直すときは、意味が変わるかで次のように分ける。

| 直し | すること | 理由 |
|---|---|---|
| 意味を変えずに、読み違いを消す直し | 人に聞かずに直し、手順6の確認で示す。PRのあとなら、指摘への返信で示す。 | 言い回しの直しのたびに止まると、人とのやり取りが増える。 |
| 意味が変わる直し（例：要件、判断、範囲の外を変える） | 止めて、人に聞く。 | 人が承認していない中身になる。 |

## 変更の記録とブランチ

- 依頼文か会話に変更の記録のパスがあれば、それを使う。
- 無ければ、今のブランチ名の`/`を`-`にした名前で、`.harness/docs/changes/`から`*-<その名前>.md`を、今の作業フォルダー、メインの作業フォルダーの順に探す。今の作業フォルダーを先にするのは、変更の記録がgitで追跡される導入先では、ブランチにコミットした変更の記録のほうが、メインの作業フォルダーに残った元の変更の記録より新しいためである。
- 見つからなければ、状態が「承認済み」の変更の記録を挙げて、どれかを人に聞く。どれも無ければ、先に`propose-change`を使う。
- 変更の記録の状態が「承認済み」でなければ、進めずに人の承認を得る。

ブランチは、次のように切る。

- 変更の記録の冒頭の表に書いたブランチ（変更の記録のブランチ）にいなければ、`git fetch origin <向き先のブランチ>`のあと`git switch --no-track -c <ブランチ名> origin/<向き先のブランチ>`で切る（ハーネスの`rules/git.md`の節「手元のマージ」）。`--no-track`を付けるのは、追跡の設定を書く`.git/config`にサンドボックスの中から書けず、付けないと`git switch`が1で終わるためである。pushは送り先を書く形なので、追跡の設定が無くても困らない。
- そのブランチがすでにあれば、`git switch <ブランチ名>`で移る。
- ほかのworktreeがそのブランチを使っていて、gitが移るのを止めたら（`is already used by worktree`）、そのworktreeの場所を人に示し、そこで続けるかを聞く。そのworktreeを、ほかのセッションが使っているか、コミットしていない変更が残っているかもしれないためである。

### 本体の会話がworktreeで動くとき

変更の記録がgitで追跡される導入先（節「変更の記録を完了にする時期」）で、今の作業フォルダーの一番上（`git rev-parse --show-toplevel`）がメインの作業フォルダーと違うときは、次のようにする。

- 変更の記録のブランチに移ったあとに、今の作業フォルダーの、メインの作業フォルダーと同じ相対パスに、変更の記録があるかを見る。
- あれば、コピーせずにそれを直す。前のセッションでコピーしてコミットした変更の記録で、メインの作業フォルダーの元の変更の記録より新しいためである。
- 無ければ、メインの作業フォルダーの変更の記録を、今の作業フォルダーの同じ相対パスへコピーし、そのコピーを直す。メインの作業フォルダーの変更の記録を直しても、今の作業フォルダーのコミットに入らず、PRに変更の記録が入らないためである。

変更の記録をworktreeへコピーしたときは、PRのあとに、メインの作業フォルダーに残った元の変更の記録を人に示し、承認を得て消す。節「並行のとき」の実装役（worktreeで動く実装のサブエージェント）がコピーしたときも同じである。残すと、マージのあとの`git merge --ff-only origin/<向き先のブランチ>`で、追跡されていないファイルとぶつかるためである。消す前に、メインの作業フォルダーで変更の記録のブランチへ移ろうとすると、gitが止めることがある（`untracked working tree files would be overwritten`）。そのときも、元の変更の記録がブランチの変更の記録より古いことを示し、承認を得て消してから移る。

## セッションの分け方

作業の手順のまとまりを終え、次のまとまりを変更の記録だけで始められるなら、新しいセッションで続けるよう人に勧める。

- 変更の記録だけで始められるとは、このセッションで読んだファイルの中身やコマンドの出力を、次のまとまりで使わないことである。
- 残りの作業の手順がこのセッションで終わる見込み（例：同じまとまりの残りの数行）なら、分けない。新しいセッションは、ルールと変更の記録を読み直すところから始まるためである。
- 並行の実装役（節「並行のとき」）は、分けない。サブエージェントは、新しいセッションを始められないためである。

分けるのは、Claude Codeがリクエストのたびに会話の全体を送るので、セッションが長いほど本体の会話の使用量が増えるためである。比べた案と測った結果は、ハーネスの本体の会話の使用量の判断の記録（`docs/decisions/0030-main-conversation-usage.md`）に書く。

勧めるときは、次のようにする。

- 勧める前に、終えた作業の手順にチェックを付け、確かめ方の結果、人が決めたこと、残っていることを変更の記録に書き、変更をcommitしてpushする。新しいセッションには、変更の記録とgitの履歴にあることしか渡らないためである。
- 自動の記憶には書かない（ハーネスのリポジトリの`.harness/docs/features/harness-folder.md`の節「自動の記憶との分け方」）。自動の記憶は、Claude Codeが、PCごとに自分で書いて次のセッションで読むメモである。
- 次のセッションの依頼文と権限のモードを、常に読むルールの節「完了の条件」のとおりに示す。依頼文には、変更の記録のパスと、チェックの無い最初の作業の手順から進めることを書く。

新しいセッションでは、変更の記録を読み、チェックの無い最初の作業の手順から進める。

## 今の説明

- 今の説明は、導入先の`.harness/docs/`に置く、コードから読み取れないこと（背景、要求、業務のルール、前提、理由）を書く文書である。書き分けは、ハーネスのリポジトリの`.harness/docs/features/harness-folder.md`の節「書き分け」に従う。
- 目次（`.harness/docs/README.md`）に今の説明の置き場所が書いてあれば、そこを直す。
- 変えた機能の説明が無ければ、`assets/feature.md`をコピーして`.harness/docs/features/<機能の名前>.md`（例：`invoice.md`）を作り、目次に足す。
- 確かめていない節は「未確認」とだけ書き、推測は変更の記録の「調べたこと」に残す。
- 判断の表の「誰が決めたか」には、判断を決めた変更の記録へのリンクを書く。変更の記録の案の表で「人の回答（YYYY-MM-DD）」と書いた判断はその日付も書き、「エージェントの案」の判断には人の回答と書かない。決めた文書を残さないときの値は、ハーネスのリポジトリの`.harness/docs/features/harness-folder.md`の節「文書の形」に従う。
- 直した今の説明の冒頭の表の「確かめたコミット」は、変更の記録を「完了」にするときに、照らしたコードが入ったコミットのSHAにする。あとで`git diff <SHA>`を動かすと、そのあとに変わったコードだけが出るためである。
  - 変更の記録がgitで追跡されない導入先では、マージを知ったときに`git fetch origin <向き先のブランチ>`を動かし、下の3つの値を順に`git merge-base --is-ancestor <SHA> origin/<向き先のブランチ>`で確かめる。0で終わった（向き先のブランチから辿れた）最初の値の`git rev-parse --short <SHA>`にする。
  - 追跡される導入先では、作業用のブランチの先頭のSHA（`git rev-parse --short <ブランチ名>`）にし、「完了」にするコミットに入れる。squashかrebaseでマージする導入先では、このSHAはマージのあとに向き先のブランチから辿れない。作業用のブランチを消したあとの別のクローンか、reflogの期限が切れてgcがそのcommitを消したあとでは、`git diff`が失敗する。

追跡されない導入先で確かめる値は、次の3つである。

1. 作業用のブランチの先頭（`<ブランチ名>`）。マージコミットかfast-forward（マージコミットを作らずにブランチの先頭を進めるマージ）の導入先で辿れ、照らしたコードそのものになる。
2. 節「ホストごとのコマンド」の「マージのcommit」の値。squashかrebaseの導入先で使う。
3. `origin/<向き先のブランチ>`の先頭。

2と3の値は、照らしたコードに無いほかのPRの変更も含み、その変更は`git diff`に出ない。2はマージの前に、3はマージを知るまでに向き先のブランチに入ったPRの変更を含む。

## レビュー役に渡すもの

レビュー役は、常に読むルールを自分で読む。セッションの始めのフックの出力は、サブエージェントに届かないためである。依頼文には、次のものを入れる。

- ハーネスの場所（フックが渡す、ハーネスのリポジトリの手元のパス）と、メインの作業フォルダー
- 依頼、変更の記録のパス、差分の範囲（例：`origin/<向き先のブランチ>...HEAD`、直しの差分ならコミットの範囲）、機械の確認の出力（手順4のテスト、lint、文章の確認の出力と、動かさなかったテストの名前と理由）
- 深さ（深いときは、担当する観点か範囲）、何回目か、前の回の指摘とその扱い

深いときは、変更の記録の冒頭の表に書いた数のレビュー役を、互いの結果を見せずに同時に動かす。

## PRの本文

導入先にPRのテンプレートがあれば、その見出しで書く（ハーネスの`rules/git.md`の節「PRの題と本文」）。変更の記録からは、次のように入れる。

| PRの本文 | 変更の記録から入れるもの |
|---|---|
| 背景 | 背景をそのまま入れる。 |
| 要求 | 要求をそのまま入れる。 |
| 方法 | 判断と作業の手順から、何をどう変えたかと、採らなかった案の理由を書く。 |
| 確かめ方 | 確かめ方の表に、別の文脈のレビューの行と、動かさなかったテストの行（節「テストと文章の確認」）を足す。 |
| 残っていること | 残っていることをそのまま入れる。 |

本文には、今の中身と、採らなかった案とその理由を書く。作業の経過（例：「1回目のレビューで直した」「最初はAにしたが、Bに変えた」）は書かない。レビューする人は今の中身で判断し、経過はコミットに残るためである。

## ホストごとのコマンド

PRを送るリモートのホストの種類（GitHubかGitLab）を、ハーネスの`rules/git.md`の節「ホストの種類」で決め、次のコマンドで読む。PRの作り方は、同じファイルの節「PRの題と本文」に書く。

| 読むもの | GitHub | GitLab |
|---|---|---|
| 公開のリポジトリか | `gh repo view --json visibility`の`visibility`が`PUBLIC` | `glab api graphql -f query='query($fullPath: ID!) { project(fullPath: $fullPath) { visibility ciConfigPathOrDefault } }' -f fullPath=<グループ>/<プロジェクト>`の`visibility`が`public`か`internal` |
| CIの結果 | `gh pr checks <番号>` | `glab api --paginate projects/<P>/merge_requests/<番号>/pipelines`で`id`の最も大きいパイプラインを選び、`glab api --paginate projects/<P>/pipelines/<パイプラインのid>/jobs`の`name`と`status` |
| マージされたか | `gh pr view <番号> --json state`の`state`が`MERGED` | `glab api projects/<P>/merge_requests/<番号>`の`state`が`merged` |
| マージのcommit | `gh pr view <番号> --json mergeCommit --jq .mergeCommit.oid` | 同じ応答の`merge_commit_sha`（`null`なら`squash_commit_sha`） |

- `<グループ>/<プロジェクト>`は、PRを送るリモートのURLのパス（例：`group/sub/project`）で、`<P>`は、その`/`を`%2F`にした形（例：`group%2Fsub%2Fproject`）である。
- GitLabの`internal`を公開として扱うのは、そのGitLabにログインしたすべての人が読めるためである。
- GraphQLの`query`の値は、判定のスクリプトが一字一句同じときだけ確認なしで通すので、空白も変えずに書く。
- GitLabの落ちたジョブのログ（`glab api projects/<P>/jobs/<ジョブのid>/trace`）は、判定のスクリプトが確認を求める。マスクしていないCI/CDの変数がログに出ることがあるので、読むときは人にそのことを伝える。

## 変更の記録を完了にする時期

変更の記録がgitで追跡されているか（`.harness/`の中のファイルが`git ls-files`に出るか）で分ける。

| 変更の記録 | いつ「完了」にするか | 理由 |
|---|---|---|
| gitで追跡されている | PRを作る前の確認のあと、状態を「完了」にしてコミットし、PRに入れる。マージのあとは書き換えない。 | 向き先のブランチへ書き換えのPRを足さずに済む。向き先のブランチに入る変更の記録は、マージされたものだけになる。 |
| 追跡されていない | マージを知ったとき（人に伝えられたか、節「ホストごとのコマンド」の「マージされたか」で見たとき）に「完了」にする。 | gitの外にあり、いつでも書き換えられる。 |

gitで追跡されている変更の記録をPRのあとに直したら、変更の記録の確かめ方と残っていることも、その直しのコミットで直す。直しでコードを変えたら、コードを直したコミットのあとに、直した今の説明の確かめたコミットを、そのコミットのSHAに直す。

## 並行のとき

人が並行を承認した変更の記録ごとに、worktreeで動くサブエージェント（実装役）を起動する（Claude Codeでは、`isolation`を`worktree`にする）。人とのやり取りは、本体の会話に集める。サブエージェントは、人に直接聞けないためである。

本体の会話は、次のことをする。

1. 実装役の依頼文に、ハーネスの場所、メインの作業フォルダー、変更の記録のパス、ブランチ名と、この手順のファイル（ハーネスの`skills/implement-change/SKILL.md`）を入れる。手順1～5を進め、手順6の候補と、決まっていない語（節「決まっていない語」）と、PRの本文の下書きを報告して止まるよう頼む。
2. すべての実装役の報告をまとめて、手順6の確認とPRの下書きを人に示す。
3. 決まっていない語の答えは、本体の会話が導入先ごとの語の一覧に書く。一覧はメインの作業フォルダーにあり、実装役はworktreeの外のファイルを書けないためである。禁止にすると決まった語と使った場所と、人のそれ以外の答えは、実装役に送る。実装役は、禁止にすると決まった語を言い換え、変更の記録に書いてコミットとpushをし、報告する。変更の記録がgitで追跡される導入先では、実装役が変更の記録の状態を「完了」にしてからコミットする（節「変更の記録を完了にする時期」）。
4. 人の確認を得て、実装役のブランチごとにPRを作り、CIの結果を読む。GitHubでは、`gh pr create`に`--head <実装役のブランチ>`を付ける。書かないと、`gh pr create`が本体の会話の作業フォルダーの今のブランチからPRを作るためである。
5. 先のPRがマージされたら、残りのブランチに`git merge origin/<向き先のブランチ>`で取り込み、テストを動かし直す。push済みの履歴は書き換えない（ハーネスの`rules/git.md`の節「手元のマージ」）。
6. PRがマージされたら、そのPRの実装役のworktreeと、手元のブランチ（worktreeに自動で付いたブランチと、変更の記録のブランチ）を人に示し、承認を得て消す。変更のあったworktreeとブランチは、自動では消えないためである。変更の記録がgitで追跡されない導入先では、消す前に、worktreeの変更の記録をメインの作業フォルダーへコピーして戻してから「完了」にする。

実装役は、場面ごとに次のことをする。

| 場面 | すること | 理由 |
|---|---|---|
| 最初に | 今の作業フォルダー（`pwd`の出力）を、報告の最初に書く。ハーネスの`rules/always-read.md`と、メインの作業フォルダーの`.harness/rules/always-read.md`を読み、`bash <ハーネスの場所>/hooks/print-environment-state.sh <今の作業フォルダー> <メインの作業フォルダー>`を動かして、環境の状態（コマンドの動かし方、ファイルの読み書きとコマンドの書き方、終了コードの読み方、働かない保護）を読む。 | 常に読むルールと環境の状態を渡すフックの出力は、サブエージェントに届かない。作業フォルダーは、再開したときに比べる。 |
| 変更の前 | `git fetch origin <向き先のブランチ>`のあと、`git switch --no-track -c <ブランチ名> origin/<向き先のブランチ>`で切る。 | worktreeのブランチ名は自動で付き、変更の記録のブランチ名と合わない。 |
| ブランチを切ったあと | メインの作業フォルダーの変更の記録を、自分のworktreeの同じ相対パスへコピーする。変更の記録は、このコピーを直す。 | worktreeの外のファイルは直せない（Claude Codeでは、worktreeの外の書き換えが断られる）。 |
| コマンドを動かすとき | コマンドは1つずつにし、パスを変数に入れずにそのまま書く。メインの作業フォルダーでは、`cd`とgit（`git -C`を含む）を動かさない。 | Claude Codeでは、メインの作業フォルダーへの`cd`とgit、パスを変数に入れた複合のコマンドが断られる。 |
| 人の判断が要るとき | 問いを報告に書いて止まる。 | 答えを受けると、文脈を保って再開できる。 |
| 再開したとき | 今の作業フォルダーが、報告の最初に書いた場所と同じかを確かめ、違えば変更せずに止まる。 | 変更の前に止まるとworktreeが消え、再開すると本体の会話の作業フォルダーで動くためである。 |
| レビュー | 自分でレビュー役を起動する。 | サブエージェントは、自分のサブエージェントを起動できる。 |
| コミット | 変更の記録がgitで追跡される導入先では、変更の記録のコピーをコミットに入れる。追跡されない導入先では、コミットしない。 | 追跡される導入先では変更の記録もPRでレビューし、追跡されない導入先のgitにはハーネスのファイルを足さない。 |

実装役が止まったら、本体の会話は、止まった理由で次のようにする。

| 止まった理由 | すること | 理由 |
|---|---|---|
| 使用量の上限 | 上限が戻ったあとに、同じ実装役に続きを頼む。 | 文脈を保ち、同じworktreeで再開する。 |
| 再開した場所が違う | 問いと答えを依頼文に足して、新しい実装役を起動する。 | 同じ実装役に答えを送り直しても、本体の会話の作業フォルダーで動く。 |
