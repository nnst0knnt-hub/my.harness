# 変更の記録を書いて承認を得る

実装の前に、1つのPRについての変更の記録を書き、人の承認を得る手順である。

- 変更の記録は、導入先（ハーネスを入れたリポジトリ）の`.harness/docs/changes/`に、PRごとに1つ置く文書である。承認したあとは、`implement-change`（変更の記録どおりに実装してPRを作るスキル）が作業の手順を進める。
- 今の説明（導入先の`.harness/docs/`に置く、導入先の今の状態を書く文書）とは、別のファイルにする。
- 分ける理由と変更の記録の形は、ハーネスのリポジトリの`.harness/docs/features/harness-folder.md`の節「`.harness/docs/`の形」に書く。

## 手順

1. 依頼を読み、変更の種類を節「変更の種類」の表から1つ選び、その種類の資料を読む。
2. ハーネスの`rules/quality.md`（変更の質を確かめる問いの一覧）を読む。導入先のコード、導入先のチームの文書、`.harness/docs/`の今の説明（目次から選ぶ）を調べる。
3. ブランチ名を、ハーネスの`rules/git.md`の節「ブランチ名」で決める。
4. `assets/change.md`をコピーし、メインの作業フォルダーに、`.harness/docs/changes/<今日の日付>-<ブランチ名の/を-にしたもの>.md`を作る（例：`2026-10-23-fix-invoice-total.md`）。メインの作業フォルダーは、`SessionStart`のフックが渡す、worktreeでない元の作業フォルダーである。
5. 変更の記録の節を、節「変更の記録の書き方」のとおりに埋める。
6. 独立した作業が複数あれば、作業ごとに変更の記録を作り、並行で進められるかを節「並行で進められるか」のとおりに示す。
7. 変更の記録を人に示して承認を得て、冒頭の表の状態を「承認済み」にする。人が頼めば、チームで議論するための資料を、節「議論のための資料」のとおりに作る。

背景、要求、要件、範囲の外、判断の5つの節（止める節）に「未確認」が残るあいだは、承認に進まず、人に聞く。推測で埋めると、人が承認した内容と実装がずれるためである（ハーネスのリポジトリの`.harness/docs/features/harness-folder.md`の節「文書の形」）。

## 変更の種類

種類の資料は、`references/`にある、種類ごとに変更の記録に書くことの表である。どの資料にも「最初に示す証拠」「確かめ方」「作業の手順の最初」の3つの項目がある。

| 種類 | 当てはまる依頼 | 資料 |
|---|---|---|
| 機能の追加 | 機能を足す。文書、テスト、ビルド、CIだけの変更も含む。 | `references/feature-addition.md` |
| 不具合の修正 | 誤った動きを直す。本番の障害を急いで直す作業と、不具合になる前に直す作業（予防保守）も含む。 | `references/bug-fix.md` |
| リファクタリング | 振る舞いを変えずに、コードの形を変える。 | `references/refactoring.md` |
| 性能の改善 | 速さや使う資源の量を変える。 | `references/performance-improvement.md` |
| 依存や環境の更新 | ライブラリやランタイムのバージョンを上げる。 | `references/dependency-update.md` |
| データの変更 | データベースのスキーマとデータを変える。 | `references/data-change.md` |
| インフラの変更 | サーバー、ネットワーク、クラウドの設定を変える。 | `references/infrastructure-change.md` |

1つの依頼が2つの種類にまたがるときは、作業を分けて変更の記録を2つにできないかを先に見る。分けられなければ、両方の資料を読み、両方の「最初に示す証拠」を確かめ方に、両方の「作業の手順の最初」を作業の手順に入れる。

## 変更の記録の書き方

| 節 | 書き方 |
|---|---|
| 冒頭の表 | 状態は「下書き」にし、確かめたコミットは、調べたときのコミットのSHA（`git rev-parse --short HEAD`）にする。レビューの深さは、ハーネスの`rules/review.md`の節「レビューの深さ」で決め、理由を書く。 |
| 背景、要求 | 背景は何が困っていたか、要求はどうなればよいかを書く。要求には、誰の何が解決すれば満たしたと言えるかを入れる。 |
| 要件 | 機能、非機能、変えない動き、制約の4つの行に、語句（「。」で終わらない語のまとまり）で書く。当てはまらない行は「なし」にする。 |
| 調べたこと | わかったことと、その出典か確かめ方（読んだコード、文書、人の回答、動かした結果）を表にする。推測は、推測と書いて、ここにだけ書く。 |
| 判断 | 論点（決めることの1つ1つ）ごとに`###`を置き、案の表（案、結果、誰が決めたか、理由）を書く。比べる案が無い判断は、判断と理由の表にする。 |
| 質の問いの答え | ハーネスの`rules/quality.md`の問いのうち、当てはまるものに答える。当てはまらない問いは書かない。 |
| 確かめ方 | 要件の項目ごとに、何で確かめるかを書き、結果の列は実装のあとに埋める。最初の行には、種類の資料の「最初に示す証拠」を書く。 |
| 作業の手順 | チェックボックスで上から行う順に書き、1つのセッションで終える量（まとまり）ごとに`###`の見出しで分ける。最初に種類の資料の「作業の手順の最初」を、最後に今の説明と目次を直す手順を書く。 |
| 残っていること | 残すものがあれば、表に1行ずつ書く。無ければ、表を消して「なし」と書く。 |

要件と判断は、次のように書く。

- 要件の変えない動きには、人が手で直した所（例：人がコミットした文の言い回し、人が会話で直すよう言った値）も入れる。エージェントが書き直すときに、人の直しを消さないためである。
- 案の表の理由には、ハーネスの`rules/quality.md`の節「案の比べ方」のとおりに、差が出る観点での得失と、優先した観点を書く。
- 案の表の「誰が決めたか」は、人が会話で答えて選んだ案なら「人の回答（YYYY-MM-DD）」、エージェントが勧めて人に個別に問わなかった案なら「エージェントの案」と書く。
- 人が変更の記録の全体を承認しても、「エージェントの案」を「人の回答」に書き換えない。あとで読むエージェントが、人がはっきり決めたことと、新しい変更の記録で見直してよいことを見分けるためである。

表と節の中身は、次のように書く。

- 確かめていない節は「未確認」とだけ書き、推測の中身は書かない。当てはまらない節は「なし」と書く。
- 表の1つの列は、語句か文のどちらかにそろえる。ハーネスの`scripts/find-list-and-table-error.sh`が、1つの列に語句と文が混ざると止めるためである。
- 「なし」「未確認」と、実装の前の「（実装のあとに、語句で書く）」は語句なので、確かめ方の結果の列も語句で書く（例：8つとも通った）。

書いたら、常に読むルールの節「書く前に読むファイル」の文章の確認を、変更の記録に当ててから人に示す。常に読むルールは、フックが毎回渡す、ハーネスの`rules/always-read.md`と導入先ごとのルールである。

人が依頼で指定した文（例：「この1文を足して」と渡された文）に、文章の確認が決まっていない語を示したら、手順7の承認を求めるときに一緒に、「この導入先でも禁止にしますか？」と聞く。表の形と答えの書き方は、ハーネスの`skills/implement-change/SKILL.md`の節「決まっていない語」のとおりにする。禁止になれば人が指定した文を言い換えるので、実装の前に人が決めるためである。

## 並行で進められるか

並行で進められるかは、次の3つで見る。どれかに当たれば、順に進めることを勧める。

- 触るファイルの重なり
- 順番に意味があるか（例：先の作業の結果を、あとの作業が使う）
- worktreeの外で共有するもの（例：DB、ポート番号、`.env`、Dockerのコンテナー）

並行を勧めるときは、変更の記録ごとの冒頭の表に、実装役（worktreeで動く実装のサブエージェント）の数、理由、使用量の見込みを書く。人が承認するまで、並行で始めない。人の承認が、常に読むルールの「サブエージェントを同時に2つ以上動かす」の確認を兼ねるためである。見込みの立て方は、ハーネスの`rules/review.md`の節「使用量の見込み」に書く。

## 議論のための資料

人が頼んだときだけ作る。変更の記録の背景、要求、判断（採らなかった案を含む）、残っていることから、読み手に合わせて書く。読み手がエンジニアでなければ、技術用語を説明するか言い換える（ハーネスの`rules/writing.md`の節「言葉」）。
